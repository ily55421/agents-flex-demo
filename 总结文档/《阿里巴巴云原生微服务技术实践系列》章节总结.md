## 第1章：Dubbo 3.0 - 开启下一代云原生微服务
**来源文件：** 【Dubbo3.0-开启下一代云原生微服务】+郭浩（项升）+2020.8.18.pdf

### 核心论点
- **问题：** 传统的微服务架构在面对云原生环境（如 Kubernetes、Service Mesh）时，存在协议不兼容、注册发现机制过重、多语言支持复杂等问题。
- **观点：** Dubbo 3.0 旨在通过应用级服务发现、新一代通信协议（Triple）以及对 Service Mesh 的原生支持，实现从“以接口为中心”到“以应用为中心”的转变，全面拥抱云原生。

### 关键概念/事件
- **应用级服务发现（Application-level Service Discovery）：** 从传统的“接口级”注册（每个接口一个节点）转变为“应用级”注册（每个应用实例一个节点），大幅降低注册中心压力，提升大规模集群下的性能。
- **Triple 协议：** 基于 HTTP/2 和 gRPC 演进的新一代协议，兼容 gRPC，支持浏览器直接调用，便于跨语言和 Mesh 集成。
- **Proxyless Mesh：** 允许 Dubbo 应用在无 Sidecar 的情况下，通过 SDK 直接对接 xDS 控制面，兼顾 Mesh 的标准化和 SDK 的高性能。
- **Dubbo 发展里程碑：** 从 2011 年阿里内部 SOA 方案，到 2018 年进入 Apache 孵化器，再到 2020 年启动 3.0 版本，标志着其从互联网架构向云原生架构的演进。

### 逻辑推演/叙事脉络
本章首先回顾了 Dubbo 的历史演变，从阿里内部 SOA 解决方案到开源、捐赠 Apache 的过程。接着分析了业界主流方案（如 Spring Cloud、gRPC、K8s Service）的优缺点，指出传统微服务在极限场景下（如数万个实例）注册中心的性能瓶颈。随后，重点介绍了 Dubbo 3.0 的核心特性：应用级服务发现如何解决性能问题，Triple 协议如何实现多语言互通和 Mesh 友好，以及 Roadmap 中关于 K8s 原生支持和柔性落地的规划。最后展示了阿里内部及外部公司的试点情况，证明新架构的可行性。

### 经典金句/数据
> “Dubbo 3.0 开启下一代微服务，核心在于应用级服务发现和 Triple 协议的支持。”

- **数据：** 在极限场景下，传统接口级注册可能产生 `10k+ * N` 的节点数量，而应用级注册将其降低至 `2K * N` 甚至更低，性能提升显著。
- **时间线：** 2020.03 开源侧交付下一代协议；2020.09 阿里内部应用落地；2021.06 K8s 原生支持和试点。

## 第2章：云原生时代消息中间件的演进路线
**来源文件：** 【云原生时代消息中间件的演进路线】+周礼（不铭）+2020.8.18.pdf

### 核心论点
- **问题：** 传统消息中间件在云原生环境下部署运维复杂，难以弹性伸缩，且与新兴的事件驱动架构（EDA）融合度不高。
- **观点：** 云原生消息服务应具备标准化、高 SLA、低成本、易用性和多样性。通过容器化、存算分离、Serverless 化以及与 Service Mesh 的集成，实现消息中间件的云原生化演进，并区分“消息”与“事件”的不同应用场景。

### 关键概念/事件
- **云原生消息服务特征：** 包括快速部署至 K8s、利用 K8s 能力低成本运维、使用 Prometheus 观测指标、逻辑资源与物理资源的按需扩缩容。
- **RocketMQ 云原生架构：** 采用存算分离架构，计算节点无状态，存储引擎支持多模存储（CommitLog、索引等），支持 Pop 消费模式以适配 Mesh 的无状态网络模型。
- **消息 vs 事件：** 消息（Message）常用于微服务间的异步解耦，发送方对处理逻辑有预期；事件（Event）代表状态变化，源端对响应无预期，适合更彻底的解耦和 EDA 架构。
- **产品矩阵：** 阿里云消息产品包括 RocketMQ（业务消息）、Kafka（大数据）、MQTT（IoT）、AMQP（RabbitMQ 兼容）、MNS（通知）和 EventBridge（事件总线）。

### 逻辑推演/叙事脉络
本章首先定义了云原生消息服务的定位和目标（高 SLA、标准化、低成本等）。接着详细阐述了 RocketMQ 在云原生环境下的架构演进，包括如何利用 K8s 进行弹性伸缩（Broker 扩缩容、PV 漂移），以及如何通过 Sidecar 模式融入 Service Mesh。随后，介绍了阿里云完整的消息产品矩阵及其适用场景。最后，深入探讨了“消息”与“事件”的区别，引出 EventBridge 在云原生事件驱动架构中的核心地位，强调了从传统消息队列向中心化事件服务能力转变的趋势。

### 经典金句/数据
> “消息是比事件更通用的抽象（Raw Data），而事件是具像化的，代表事情的发生、条件和状态的变化。”

- **数据：** 双 11 消息收发 TPS 峰值过亿，日消息收发总量 3 万亿；消息发布平均响应时间不超过 3 毫秒。
- **架构亮点：** RocketMQ 是国内第二个成功进入 Service Mesh 官方社区的中间件产品。

## 第3章：进击的 Spring Cloud Alibaba —— 框架与服务
**来源文件：** 【进击的 Spring Cloud Alibaba —— 框架与服务】+陈曦（良名）+2020.8.18.pdf

### 核心论点
- **问题：** Java 开发者在使用 Spring Cloud 构建微服务时，面临组件选型复杂、配置繁琐、云原生环境适配难等问题，且缺乏从开发到部署的一站式体验。
- **观点：** Spring Cloud Alibaba 不仅是 Spring Cloud 标准的最佳实现，更通过“框架+服务”的模式，提供 Java 工程脚手架和 Sandbox 云沙箱等开发者服务，打造完整的 Java 云原生开发体验。

### 关键概念/事件
- **Spring Cloud Alibaba 定位：** 对 Spring Cloud 标准的具体实现，整合了 Nacos（注册配置）、Sentinel（熔断限流）、Dubbo（RPC）、Seata（分布式事务）等阿里开源中间件。
- **对比优势：** 相比 Spring Cloud Netflix（已停更）和其他实现，SCA 提供了更完整的分布式解决方案，特别是在服务熔断、分布式事务和服务路由方面。
- **Java 工程脚手架：** 提供一站式应用骨架生成，支持多种架构（MVC、DDD、Serverless），自动整合阿里云组件，内置文档和案例。
- **Sandbox 云沙箱：** 提供免费的云上实验环境，用户可一键部署分布式应用，无需关心底层资源和计费，支持 Web-IDE 在线修改和调试，降低学习门槛。

### 逻辑推演/叙事脉络
本章首先介绍了微服务和云原生的基本概念及挑战，指出 Spring 家族在 Java 微服务领域的统治地位。接着，详细对比了 Spring Cloud 各套实现方案，突出 Spring Cloud Alibaba 的功能完整性和活跃度。随后，重点阐述了从“框架”到“服务”的战略转变，介绍了两大核心开发者服务：Java 工程脚手架（解决起步难问题）和 Sandbox 云沙箱（解决环境搭建和学习成本问题）。最后，展示了 SCA 的发展规划，包括持续集成更多阿里云服务和丰富教学案例。

### 经典金句/数据
- **数据：** Spring Cloud Alibaba GitHub Star 数 15K+，被依赖次数 6000+，使用公司数 1000+。
- **对比结论：** “Spring Cloud Alibaba 是 Spring Cloud 最好的实现。”（基于功能覆盖度和社区活跃度）

## 第4章：Sentinel 微服务高可用容错最佳实践
**来源文件：** 【Sentinel 微服务高可用容错最佳实践】+赵亦豪（宿何）+2020.8.18.pdf

### 核心论点
- **问题：** 微服务架构中，激增流量、依赖不稳定、慢 SQL 等问题容易导致系统雪崩，传统静态限流配置难以应对动态变化的系统负载。
- **观点：** Sentinel 作为面向分布式服务架构的高可用防护组件，通过多维度的流控降级、实时秒级监控和自适应系统保护，提供全方位的高可用防护，尤其强调“兜底防护”和“强弱依赖梳理”。

### 关键概念/事件
- **核心场景：** 流量控制（QPS/线程数）、熔断降级（慢调用/异常比例/异常数）、系统自适应保护（Load/CPU/RT 等指标）。
- **热点参数限流：** 针对热点商品或用户 ID 进行细粒度流控，结合 LRU 淘汰策略和 Token Bucket 算法。
- **集群流控：** 解决单机流控不均问题，通过 Token Server 统一分配配额，适用于小流量集群或全局频次控制。
- **自适应系统保护：** 基于 TCP BBR 算法原理，根据系统 Load 和 RT 动态估算系统容量，自动调整入口流量，防止系统打满。

### 逻辑推演/叙事脉络
本章首先列举了微服务可用性面临的典型场景（激增流量、依赖故障、慢 SQL 等），引出对高可用防护的需求。接着，详细介绍了 Sentinel 的核心功能和配置实践，包括如何梳理核心接口、配置流控规则、设置熔断降级策略。特别强调了系统自适应保护作为“兜底”机制的重要性。随后，讲解了 Sentinel 在云原生环境下的集成，如与 Service Mesh（Envoy+Istio）的结合，通过 RLS Token Server 提供全局流控。最后，总结了全方位高可用防护体系，涵盖从客户端到服务端、从应用到基础设施的多层防护。

### 经典金句/数据
> “You NEED Sentinel：多维度的流控降级能力，秒级实时监控与动态规则管理。”

- **数据：** 4 个 9 可用性对应年停机时间 52.6 分钟，5 个 9 对应 5 分钟。
- **原理：** 系统自适应保护公式：`min RT * max QPS = estimated capacity`。

## 第5章：云原生微服务下混沌工程实践
**来源文件：** 【云原生微服务下混沌工程实践】+肖长军（穹谷）+2020.8.18.pdf

### 核心论点
- **问题：** 云原生微服务架构复杂度极高，传统测试方法难以覆盖所有故障场景，系统在生产环境中面临不可预知的风险。
- **观点：** 混沌工程是在分布式系统上进行实验的学科，旨在通过主动注入故障（如延迟、异常、资源耗尽），验证系统容错能力，建立抵御生产环境问题的信心。ChaosBlade 工具链使得混沌实验简单易用、无侵入且可扩展。

### 关键概念/事件
- **混沌工程定义：** “What does not kill me, makes me stronger.” 通过实验提升系统容错性。
- **ChaosBlade 工具：** 遵循混沌实验模型，支持基础资源（CPU/内存/网络）、应用服务（Java/C++/Go 等）、容器服务（Docker/K8s）和云平台（ECS/OSS 等）的故障注入。
- **实验模型：** 包含范围（Scope）、目标（Target）、动作（Action）和匹配器（Matcher），支持声明式配置（YAML）。
- **实践案例：** 数据库调用延迟实验、下游服务超时实验、实例异常实验等，通过监控指标（如 RT、QPS、慢 SQL 数）验证系统是否符合预期容错假设。

### 逻辑推演/叙事脉络
本章首先介绍了云原生架构下的稳定性挑战，引出混沌工程的概念和价值。接着，详细展示了 ChaosBlade 工具的架构和能力，包括其支持的多种执行器（OS/JVM/K8s/Aliyun）和丰富的故障场景。随后，通过具体的实践案例（如数据库延迟、服务超时），演示了如何定义稳态假设、实施混沌实验、监控指标变化并进行问题排查。最后，介绍了 AHAS Chaos 平台如何将混沌工程工程化、平台化，支持日常演练、突袭演练等多种模式，帮助企业系统化地提升系统稳定性。

### 经典金句/数据
> “混沌工程是在分布式系统上进行实验的学科，旨在提升系统容错性，建立系统抵御生产环境中发生不可预知问题的信心。”

- **工具特点：** 场景丰富度高、使用简洁、动态加载无侵入、扩展方便。
- **案例结论：** 通过混沌实验发现，某系统在下游服务超时时未自动恢复，经排查需配置熔断策略以实现快速失败。
