## 第1章：微服务在云原生时代的演进

### 1. 核心论点
- **主要问题**：在云原生时代，微服务架构面临运维复杂度高、多语言支持困难、安全治理挑战等问题，如何演进以适应容器化、Kubernetes 及 Serverless 环境？
- **核心观点**：微服务架构正从传统的“代码级耦合”向“运行时解耦”演进，通过 Sidecar 模式（如 Istio）和分布式运行时（如 Dapr）实现业务逻辑与中间件能力的分离，同时结合可信安全体系构建完整的云原生微服务生态。

### 2. 关键概念/事件
- **微服务生命周期与运维挑战**：近50%的企业认为微服务的主要挑战在于更复杂的运维。云原生通过 Kubernetes 将微服务生命周期标准化（Pod、容器、服务发现、监控等）。
- **流量治理与 Service Mesh**：通过 Envoy 等数据平面和 Istio 等管控平面，实现流量劫持、负载均衡、熔断降级等能力，使业务代码无需关心网络通信细节。
- **分布式运行时 Dapr**：Dapr（Distributed Application Runtime）提供标准化的 HTTP/gRPC API，将状态管理、发布/订阅、资源绑定等中间件能力从业务代码中剥离，支持多语言、可插拔的组件模型。
- **可信安全体系**：基于 SPIFFE/SPIRE 标准，建立包含网络身份、节点身份、应用身份的可信身份体系，结合硬件可信平台（TPM/MOC）实现机密计算和安全通道。
- **阿里云 EDAS 3.0**：提供以应用视角的全生命周期托管，支持 Spring Cloud/Dubbo 等主流框架无缝上云，具备无损下线、金丝雀发布、智能诊断等企业级治理能力。

### 3. 逻辑推演/叙事脉络
本章首先回顾了微服务从传统 IT 到云托管再到云原生平台的演进路径，指出容器化和 Kubernetes 成为新的基础设施标准。接着，分析了微服务在流量治理方面的痛点，引出 Service Mesh（Istio）作为解决跨语言、非侵入式流量管理的方案。随后，进一步提出“运行时解耦”的概念，介绍 Dapr 如何通过标准化 API 屏蔽底层中间件差异，简化开发模型。最后，探讨了微服务的安全问题，提出基于身份的可信安全架构，并展示了阿里云 EDAS 如何将上述理念产品化，提供一站式的微服务治理平台。

## 第2章：基于能力的系统架构 (Capability Oriented Architecture for cloud and edge)

### 1. 核心论点
- **主要问题**：智能应用需要持续的人工智能及其他复杂能力，但硬件固化、SDK 耦合或云服务依赖往往限制了灵活性和可移植性，如何构建一种平台无关、位置无关、技术无关的架构？
- **核心观点**：提出“基于能力的架构”（COA），主张开发者应专注于声明“需要什么能力”（Intent），而非“如何实现能力”。系统通过动态发现、组合和执行能力提供者（本地、边缘或云端），实现非功能性需求（如延迟、成本）与功能需求的最佳匹配。

### 2. 关键概念/事件
- **能力交付模式的类比**：
    - **电池（集成方案）**：类似 ASIC/FPGA，硬件固化，性能高但灵活性差。
    - **充电宝（本地方案）**：类似 Library/SDK 或 Container，本地异进程，有一定灵活性但需自行管理。
    - **电源插座（SOA）**：类似 Cloud Service，基于服务架构，按需获取，完全解耦。
- **COA 核心原则**：
    - **Platform/Location/Technology Agnostic**：平台、位置、技术无关。
    - **动态发现与组合**：基于功能和非功能性需求（如延迟、成本）动态选择能力提供者。
    - **意图驱动（Intent-Driven）**：使用自然语言或声明式 API 表达需求（如 `lets.detect face`）。
- **系统架构组件**：
    - **Intention Parser（意图解析器）**：解析用户请求。
    - **Plan Builder/Coordinator（计划构建/协调器）**：制定执行计划，选择能力提供者。
    - **Acquisition Agent（获取代理）**：执行调用。
    - **Registry（注册库）**：管理可用能力及其元数据。
- **示例场景**：脸部识别、物品追踪、文字总结等，通过统一接口调用不同后端实现。

### 3. 逻辑推演/叙事脉络
本章开篇通过手机电力供应的类比（电池 vs 充电宝 vs 插座），引出智能应用对 AI 能力需求的类似演进路径：从硬件固化到 SDK 耦合，最终走向基于服务的解耦架构。作者指出当前开发者过于关注能力的“交付方式”（如选择哪个云厂商、哪种 SDK），而应转向关注“能力本身”。由此提出 COA 架构，详细阐述了其核心组件：意图解析、计划协调、动态发现和代理执行。最后，通过几个具体的代码示例（如 `lets.track`）展示 COA 如何简化开发，并强调该架构能根据环境上下文（如网络状况、成本约束）动态选择最优的能力提供者（本地缓存、边缘节点或云端服务）。

### 4. 经典金句/数据
> “Developer: focus on capability instead of delivery.”（开发者：专注于能力，而不是能力的交付。）

> “Operator: flexible and precise system control.”（运营者：灵活而精确的系统控制。）

> “Choose capability vendor based on environmental context.”（根据环境上下文选择能力提供者。）

> “Lets.summarize(‘sample.txt’).out(‘summary.txt’).run()”（通过声明式 API 调用文本总结能力，屏蔽后端实现细节。）
