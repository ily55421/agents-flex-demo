# 《RocketMQ使用排查指南》章节总结

## 第1章：什么是消息队列 RocketMQ

### 1. 核心论点

- **问题**：什么是消息队列RocketMQ？它解决了哪些核心问题？
- **观点**：RocketMQ是一款低延迟、高并发、高可用的分布式消息中间件。其核心价值在于为分布式系统提供**异步解耦**和**削峰填谷**能力，同时支持顺序消息、定时/延时消息和分布式事务消息等高级特性。

### 2. 关键概念/事件

- **核心组件**：
  - **Name Server**：提供命名服务，用于Broker的发现和路由信息的管理。
  - **Broker**：消息中转角色，负责消息存储和转发，分为Master和Slave。
  - **生产者（Producer）**：消息发布者。
  - **消费者（Consumer）**：消息订阅者。
- **应用场景**：
  - **削峰填谷**：在秒杀等流量高峰场景中，将请求先写入消息队列，再由后端系统异步处理，保护下游系统不被冲垮。
  - **异步解耦**：如用户注册后，注册系统只需将消息写入队列即可返回，邮件和短信通知系统异步消费，缩短响应时间，解耦系统依赖。
  - **分布式事务一致性**：通过**事务消息**（半事务消息+本地事务执行+提交/回滚）保证跨系统（如注册系统和邮件系统）数据的最终一致。
- **消息类型**：普通消息、定时/延时消息、全局/分区顺序消息、事务消息。

## 第2章：RocketMQ快速入门教程

### 1. 核心论点

- **问题**：如何快速上手使用阿里云消息队列RocketMQ？
- **观点**：通过开通服务、创建资源（实例、Topic、Group ID）、获取接入点、配置AccessKey，并使用官方TCP Java SDK的示例代码，即可快速完成消息的发送和订阅。

### 2. 关键概念/事件

- **资源创建步骤**：
  - **创建实例**：在控制台选择地域（公网或内网），创建实例作为资源容器。
  - **创建Topic**：在实例下创建Topic，需选择消息类型（普通、顺序、定时/延时、事务）。
  - **创建Group ID**：为消费者（或生产者）创建标识，TCP和HTTP协议的Group ID需分别创建。
- **接入点**：TCP协议接入点是实例级别的；HTTP协议接入点是地域级别的，需额外指定实例ID。
- **示例代码关键参数**：
  - `GROUP_ID`：控制台创建的Group ID
  - `AccessKey` / `SecretKey`：RAM用户的AK/SK用于鉴权
  - `NAMESRV_ADDR`：TCP接入点域名
- **消费验证**：在控制台Group管理页面查看“是否在线”和“订阅关系一致”来判断订阅是否成功。

### 3. 逻辑推演/叙事脉络

本章按实际操作顺序展开。先指导用户开通服务，然后逐步演示在控制台创建实例、Topic和Group ID的过程，并强调网络限制（Topic和Group ID必须在同一地域同一实例下才能互通）。接着说明如何获取AccessKey和接入点。最后，分别给出TCP Java SDK发送消息和订阅消息的完整代码示例，并说明如何在控制台验证订阅是否成功。本章是一个“Hello World”级别的快速入门指南。

## 第3章：发送问题排查

### 1. 核心论点

- **问题**：消息发送过程中常见的问题有哪些？如何排查和解决？
- **观点**：发送问题主要集中在性能（耗时久）、路由（No route info）、限流（broker busy）、超时、权限、消息体过大等方面。排查时需逐步确认Topic/Group ID是否存在、接入点配置是否正确、网络是否通畅、AK/SK是否有权限、SDK版本是否为最新等。

### 2. 关键概念/事件

- **No route info of this topic**：原因多为Topic不存在、接入点错误、网络不通（telnet失败）、AK/SK无权限、实例地域不匹配（公网与非公网）。
- **system busy / broker busy**：服务端压力大或抖动导致。SDK有重试机制，偶发一般无影响；持续出现需反馈技术支持。
- **发送超时**：可能原因包括服务升级、网络闪断、服务器防火墙、带宽打满、应用FullGC。
- **消息体过大**：消息体最大4MB，建议4KB以内；消息属性最大32KB。超过限制会报错`CODE: 13`。
- **权限异常**：`AuthenticationException` 通常是因为AK/SK所属账号与创建Topic/GID的账号不一致，或使用了1.7.9版本SDK的鉴权bug。
- **Php http接入报Internal error**：后端记录有网络抖动等异常，需提供实例ID等信息反馈技术支持。

### 3. 逻辑推演/叙事脉络

本章采用“问题-原因-解决方案”的FAQ结构。分别针对发送耗时久、No route info、broker busy、发送超时、连接异常（接入点混用）、各语言SDK报错（Python、PHP）、NumberFormatException（SDK版本低）、权限异常、Broker in slave mode（日志报错不影响）、消息体过大、EDAS环境部署失败、fetch name server address exception、not set any response code、UnknownHostException、消息不合法等多个典型错误，逐一给出排查思路和解决方法。每个问题都配有错误日志片段或控制台截图说明。

### 4. 经典金句/数据

> “消息体大小最大为4MB，一般建议发送的消息体在4kb之内（性能最佳）。” (p.36)

> **排查命令**：`telnet brokerip port`、`ping brokerip`、`nslookup onsaddr-internet.aliyun.com`。

## 第4章：消费问题排查

### 1. 核心论点

- **问题**：消息消费过程中常见的问题有哪些？如何排查堆积、重试、订阅关系不一致等问题？
- **观点**：消费问题主要包括消息堆积、负载不均、重复消费、重试失败、订阅关系不一致等。排查时需检查消费者线程状态（BLOCKED/WAITING）、消费能力、订阅关系一致性（同一个Group ID下所有实例的Topic和Tag必须完全一致）、广播模式特性（不支持重试和消费进度存储）等。

### 2. 关键概念/事件

- **消息堆积排查**：
  - 使用`jstack`查看`ConsumeMessageThread`状态：`BLOCKED`说明线程被阻塞；`WAITING`且堆栈为`LinkedBlockingQueue.take`是正常等待消息，其他则可能是资源紧张导致消费慢。
  - 日志中出现`flow control`警告说明消费能力不足，拉取被暂停。
- **负载不均原因**：分区顺序消息中`shardingKey`设置不合理导致消息集中；集群消费模式下消费能力饱和后无法再均衡。
- **订阅关系不一致**：同一个Group ID下的所有Consumer实例订阅的Topic和Tag必须完全一致，否则会导致消费逻辑混乱、消息丢失或重复消费。
- **消息重试机制**：集群消费模式下，消费失败返回`Action.ReconsumeLater`会触发重试，默认重试16次后进入死信队列。广播模式不支持重试。
- **重置消费位点限制**：仅集群消费模式支持，且消费者必须在线。重试队列中的消息无法通过“从最新位点开始消费”清除，需用“按时间点重置”。

### 3. 逻辑推演/叙事脉络

本章按问题类型组织。**堆积问题**：详细分析Java进程堆积（jstack排查线程状态）、消费者负载不均（分配策略及消费能力上限）、广播模式堆积（无效数据）、实时堆积量与客户端不一致（包含重试队列）。**投递重试问题**：解释消费超时后的重试间隔（10秒）、重复投递（需幂等）、重试失败一直重试（业务逻辑问题）。**订阅关系问题**：强调订阅关系不一致的严重后果。**常见异常报错**：列出启动找不到GID、消费线程卡住、新GID不消费历史消息、全局顺序消息只有一个消费者消费、延迟消息被提前消费、顺序消息乱序、消息未被消费、重置位点失败、发送方与订阅方msgid不一致（事务消息取transactionId）、消费者离线、批量消费不起作用等问题的原因和解决方案。

### 4. 经典金句/数据

> “订阅关系一致意味着同一个消费者GroupID下所有的消费者实例需在以下两方面均保持一致：订阅的Topic必须一致，订阅的Topic中的Tag必须一致。” (p.57)

> **重试默认值**：无序消息最大重试16次，顺序消息无限重试。 (p.105)

## 第5章：其他问题排查

### 1. 核心论点

- **问题**：除了发送和消费，使用RocketMQ时还可能遇到哪些问题？如控制台显示异常、计费、日志、权限等。
- **观点**：控制台数据（如堆积Top）可能存在延迟；Topic名称在全阿里云全局唯一（无命名空间实例）；计费涉及API调用次数（包含长轮询）、Topic资源占用费（2元/天）；日志中出现特定信息（如`updateConsumeOffsetToBroker`）通常是正常行为；权限策略中的IP限制必须是公网IP/宿主机IP。

### 2. 关键概念/事件

- **控制台数据延迟**：“实例详情-数据统计”中的消息堆积Top是采样数据，有延迟，应以“Group管理-消费者状态”中的实时数据为准。
- **Topic全局唯一**：无命名空间的实例下，Topic名称在全阿里云全局唯一，已被其他用户占用时会提示已存在。
- **API计费**：API请求次数 = 发送消息API次数 + 订阅消息API次数 + 长轮询API次数。每个队列每15秒一次长轮询，即使无消息也会产生费用。
- **Topic资源占用费**：2元/天/个Topic，按天计费，第二天扣费。
- **日志说明**：`[persistAll]`表示消费进度已持久化；`[TIMEOUT_CLEAN_QUEUE]`表示服务端压力大；`the consumer's subscription not latest`是负载均衡正常机制；`signature validate by dauth failed`是AK/SK错误。
- **权限问题**：`AliyunMQRReadOnlyAccess`只读权限下仍可创建和删除Group ID（产品粒度不支持细粒度控制）。

本章涵盖控制台、告警、计费、日志、权限、使用常见问题等六大类。控制台部分解释了数据统计延迟、Topic全局唯一、消费验证显示多余消费者等现象。告警部分说明了报警规则只能被创建账号查看、未收到短信的可能原因（地域、手机号、消费者在线）。计费部分详细解释了API调用次数的构成（含长轮询）、标准版TPS限制（5000条/秒）、Topic资源占用费、未使用仍扣费的原因。日志部分列举了16种常见日志信息的含义和解决方案。权限部分澄清了IP限制和只读权限的实际表现。最后回答了如何删除消息（无法主动删除，3天自动清理）、本地IDC接入（专线/VPN或HTTP公网）、经典网络切VPC是否影响（内网接入点不受影响）、是否支持消息优先级（不支持）等常见问题。
