# MySQL 索引优化实战笔记总结

## 第一章：索引原理

### 1. 索引概述
*   **定义**：MySQL 存储引擎用于快速查找记录的一种数据结构，本质是排好序的数据结构。
*   **物理存储**：
    *   **MyISAM**：数据文件与索引文件分离，索引文件保存数据记录的地址。
    *   **InnoDB**：表数据本身按照 B+Tree 组织，`.ibd` 文件包含数据+索引。

### 2. 常见数据结构演变
*   **二叉查找树 (BST)**：
    *   左子节点 < 当前节点 < 右子节点。
    *   **缺点**：有序数据插入时会退化为单向链表，查询效率低。
*   **平衡二叉树 (AVL)**：
    *   左右子树高度差最大为 1，通过旋转保持平衡。
    *   **优点**：查找效率高，避免退化。
    *   **缺点**：节点只存一个关键字，树过高导致 IO 次数多；每次操作获取数据少。
*   **B-Tree (多路平衡查找树)**：
    *   **特点**：一个节点可存多个关键字和子树，降低树的高度（矮胖结构），减少 IO。
    *   **缺点**：节点存储 Data 数据，若数据大则节点容纳 Key 少，树变高；不支持高效的范围查询。
    *   **应用**：文件系统、MongoDB。
*   **B+Tree (MySQL InnoDB 默认)**：
    *   **优化点**：
        1.  **非叶子节点只存索引（Key+指针）**，不存数据，单页能容纳更多索引，树更矮，IO 更少。
        2.  **所有数据存在叶子节点**，且叶子节点通过双向链表连接，适合范围查询和排序。
        3.  **查询稳定**：必须走到叶子节点，性能波动小。
    *   **容量估算**：
        *   页大小 16KB。
        *   假设主键 int(4B) + 指针(6B)，根节点可存 ~1600 个指针。
        *   假设行记录 1KB，叶子节点存 16 条记录。
        *   高度为 2 的树可存：$1600 \times 16 \approx 2.5$ 万条。
        *   高度为 3 的树可存：$1600 \times 1600 \times 16 \approx 4000$ 万条。
        *   **结论**：千万级数据通常只需 3 层树，IO 次数极少。

### 3. Hash 索引
*   **原理**：基于 Hash 表，Key-Value 结构。
*   **优点**：等值查询极快（理论 O(1)）。
*   **缺点**：不支持范围查询、排序、模糊查询；Hash 冲突时性能下降。
*   **应用**：Memory 引擎，InnoDB 不支持显式创建 Hash 索引（自适应 Hash 除外）。

### 4. 聚簇索引与非聚簇索引
*   **聚簇索引 (Clustered Index)**：
    *   **InnoDB**：数据与索引在一起。叶子节点存储完整行数据。
    *   **建立规则优先級**：主键 > 第一个非空唯一列 > 隐藏 row_id。
    *   **优点**：数据访问快，相关数据物理相邻。
    *   **缺点**：随机主键（如 UUID）导致页分裂和随机 IO；二级索引查询需**回表**。
*   **非聚簇索引 (Secondary Index)**：
    *   **MyISAM**：索引和数据分离，叶子节点存物理地址。
    *   **InnoDB 二级索引**：叶子节点存**主键值**。查询时需通过主键去聚簇索引查找数据（回表）。
*   **关键概念**：
    *   **回表**：通过二级索引找到主键，再查聚簇索引获取完整数据。
    *   **覆盖索引**：索引包含查询所需所有字段，无需回表。
    *   **索引下推 (ICP)**：MySQL 5.6+，在索引遍历过程中先判断非索引列条件，减少回表次数。
*   **主键选择建议**：
    *   **自增 ID**：顺序写入，减少页分裂，性能好。
    *   **UUID**：随机 IO，页分裂频繁，空间占用大。分布式场景推荐**雪花算法**。

## 第二章：Explain 性能分析

### 1. Explain 核心字段
*   **id**：查询序列号，表示执行顺序。
*   **select_type**：查询类型（SIMPLE, PRIMARY, SUBQUERY, DERIVED, UNION 等）。
*   **table**：涉及的表名。
*   **type**：**最重要指标**，访问类型。
    *   **性能排序**：`system > const > eq_ref > ref > range > index > ALL`
    *   **system/const**：主键/唯一索引精确匹配。
    *   **eq_ref**：连接查询中，关联字段为主键或唯一索引。
    *   **ref**：普通索引等值查询。
    *   **range**：索引范围查询 (`between`, `in`, `>`, `<`)。
    *   **index**：全索引扫描（比全表快，但仍需优化）。
    *   **ALL**：全表扫描（必须优化）。
*   **possible_keys**：可能用到的索引。
*   **key**：实际使用的索引。
*   **key_len**：索引使用的字节数，越长说明利用越充分。
*   **ref**：连接查询中驱动表关联字段。
*   **rows**：估算扫描行数。
*   **Extra**：额外信息。
    *   `Using filesort`：需要文件排序（性能差，需优化）。
    *   `Using temporary`：使用临时表（性能差，需优化）。
    *   `Using where`：未使用索引覆盖，需回表或过滤。
    *   `Using index`：覆盖索引，无需回表（性能好）。
    *   `Using index condition`：使用了索引下推。

## 第三章：高性能索引创建及使用策略

### 1. 创建策略
*   **数据类型尽量小**: 节省空间，提高内存缓存率，提升 IO 效率。
*   **选择性高**: `COUNT(DISTINCT col) / COUNT(*)` 越接近 1 越好。
*   **前缀索引**: 针对长字符串，选取合适前缀长度以平衡选择性和空间。**缺点**：不支持 Order By/Group By/覆盖索引。
*   **联合索引原则**:
    *   选择性高的列放前面。
    *   遵循**最佳左前缀法则**。
    *   避免冗余索引。
*   **三星索引理论**:
    1.  **一星**：索引将相关记录放在一起（缩小扫描范围）。
    2.  **二星**：索引顺序与查询排序一致（避免 Filesort）。
    3.  **三星**：索引包含查询所有字段（覆盖索引，避免回表）。
    *   *注：同时满足三星较难，通常追求满足两星。*

### 2. 使用策略（索引失效场景）
*   **最佳左前缀法则**：联合索引 `(a,b,c)`，查询必须从 `a` 开始，不能跳过中间列。
*   **不在索引列做操作**：函数、计算、类型转换会导致索引失效。
    *   错误：`WHERE LEFT(name, 4) = 'test'`
    *   正确：`WHERE name LIKE 'test%'`
*   **范围条件放最后**：范围查询后的列索引失效。
    *   `WHERE a=1 AND b>10 AND c=1` -> `c` 的索引失效。
*   **Like 查询**：
    *   `%` 在左边 (`%abc`)：索引失效。
    *   `%` 在右边 (`abc%`)：索引有效。
    *   **解决左边模糊**：使用覆盖索引。
*   **避免 NULL 判断、!=、OR**：
    *   `IS NULL`/`IS NOT NULL`、`!=`、`OR` 往往导致索引失效或全表扫描。
    *   建议字段设置为 `NOT NULL`，默认值代替 NULL。
    *   `OR` 可拆分为 `UNION ALL`。

## 第四章：慢查询日志分析

### 1. 慢查询配置
*   `slow_query_log`: 开启日志。
*   `long_query_time`: 阈值（默认 10s，建议设为 1s 或更低）。
*   `log_queries_not_using_indexes`: 记录未使用索引的 SQL。

### 2. 优化思路
*   **定位瓶颈**：IO（数据访问多）、CPU（运算复杂）、网络。
*   **Explain 分析**：关注 type, rows, Extra。
*   **小结果集驱动大结果集**：Join 时，让数据量小的表做驱动表。
*   **索引排序**：利用索引有序性避免 Filesort。
*   **只取需要的列**：禁止 `SELECT *`，促进覆盖索引。
*   **拆分复杂 SQL**：避免过多 Join 和子查询，可在应用层组装。
*   **高并发优先**：优先优化执行频率高、影响大的 SQL。

## 第五章：JOIN 优化

### 1. 驱动表与被驱动表
*   **Left Join**：左表为驱动表。
*   **Right Join**：右表为驱动表。
*   **Inner Join**：MySQL 优化器自动选择小表作为驱动表。
*   **原则**：小表驱动大表，减少外层循环次数。

### 2. JOIN 算法
*   **Simple Nested Loop (SNL)**：双层循环，效率极低 ($N \times M$)。
*   **Index Nested Loop (INL)**：被驱动表连接字段有索引。效率取决于驱动表行数 $\times$ 索引高度。
*   **Block Nested Loop (BNL)**：无索引时使用。利用 `join_buffer` 缓存驱动表数据，减少被驱动表扫描次数。
    *   优化：增大 `join_buffer_size`，减少 SELECT 字段数量。

### 3. IN vs EXISTS
*   **IN**：先执行子查询，结果缓存，再执行主查询。
    *   **适用**：子查询结果集小，主查询表大且有索引。
*   **EXISTS**：先执行主查询，逐行判断子查询是否存在。
    *   **适用**：主查询结果集小，子查询表大且有索引。
*   **口诀**：小表驱动大表。`IN` 适合外表大内表小；`EXISTS` 适合外表小内表大。

## 第六章：ORDER BY 与 GROUP BY 优化

### 1. ORDER BY 优化
*   **两种排序方式**：
    1.  **索引排序**：利用索引有序性，Extra 显示 `Using index`。
    2.  **文件排序 (Filesort)**：Extra 显示 `Using filesort`，性能差。
*   **Filesort 实现**:
    *   **全字段排序**：取出所有字段排序，速度快但耗内存。
    *   **RowID 排序**：取出 RowID 和排序字段排序，再回表取数据，省内存但多一次 IO。
    *   MySQL 根据 `max_length_for_sort_data` 自动选择。
*   **避免 Filesort 技巧**：
    *   排序字段建立联合索引。
    *   遵循最左前缀。
    *   排序方向一致（都 ASC 或都 DESC）。
    *   WHERE 条件中的范围查询后不能有排序字段。

### 2. GROUP BY 优化
*   **原理**：GROUP BY 默认会进行排序（为了聚合和可读性）。
*   **优化方案**：
    1.  **ORDER BY NULL**：如果不需要排序，显式添加 `ORDER BY NULL` 禁用默认排序。
    2.  **索引优化**：为 GROUP BY 字段建立索引。
    3.  **临时表优化**：
        *   调整 `tmp_table_size` 和 `max_heap_table_size`，尽量使用内存临时表。
        *   大数据量使用 `SQL_BIG_RESULT` 提示直接使用磁盘临时表（数组结构），避免 B+ 树维护开销。

## 第七章：MySQL 查询成本计算

### 1. 成本构成
*   **I/O 成本**：读取页面到内存。常数约 1.0。
*   **CPU 成本**：检测记录条件、排序。常数约 0.2。

### 2. 优化器选择逻辑
1.  找出所有可用索引。
2.  计算全表扫描成本：`页数 * 1.0 + 行数 * 0.2`。
3.  计算各索引扫描成本：
    *   二级索引范围扫描 I/O。
    *   预估回表行数。
    *   回表 I/O 成本 + CPU 成本。
4.  对比选择成本最低的方案。

### 3. 连接查询成本
*   **公式**：`总成本 = 驱动表单次访问成本 + (驱动表扇出值 * 被驱动表单次访问成本)`
*   **扇出值 (Fanout)**：驱动表查询结果产生的行数。
*   **优化目标**：最小化驱动表扇出值，并为被驱动表选择最优访问路径（通常是索引）。
*   **查看成本**：`EXPLAIN FORMAT=JSON` 可查看详细的 `cost_info`。

## 第八章：索引优化实战

### 案例 1：单表优化 (用户通讯录)
*   **场景**：`LIKE '%李%'` 且 `ORDER BY user_id`。
*   **问题**：全表扫描 + Filesort。
*   **优化**：
    1.  建立联合覆盖索引 `(user_id, name, mobile)`。
    2.  利用覆盖索引避免回表。
    3.  注意：`LIKE '%...'` 仍可能导致无法利用索引过滤，但覆盖索引可减少 IO。若必须前模糊，考虑搜索引擎。
*   **场景**：分页 `LIMIT 100000, 100`。
*   **问题**：深分页导致扫描大量无效数据。
*   **优化**：
    1.  **子查询优化**：先查偏移量的 ID，再 `WHERE id >= target_id LIMIT 100`。
    2.  **延迟关联**：利用覆盖索引查出主键，再 Join 原表。

### 案例 2：多表优化 (借款系统)
*   **场景**：Left Join 查询认证用户及紧急联系人。
*   **问题**：全表扫描。
*   **优化**：
    1.  为被驱动表（右表）的连接字段 `user_id` 加索引。
    2.  确保驱动表（左表）数据量尽可能小（可通过 WHERE 预过滤）。
*   **场景**：GROUP BY 统计紧急联系人数量。
*   **问题**：Using temporary, Using filesort。
*   **优化**：添加 `ORDER BY NULL`。
*   **场景**：低选择性字段索引失效。
    *   `audit_mod_cde` (审核模式) 只有两个值，区分度低。
    *   **现象**：即使加了索引，优化器也可能选择全表扫描，或者扫描行数巨大。
    *   **优化**：
        1.  对于低区分度字段，单独索引意义不大。
        2.  组合其他高区分度字段（如时间范围 `apply_time`）建立联合索引。
        3.  利用 **MRR (Multi-Range Read)** 优化随机 IO 为顺序 IO。

## 核心总结与建议

1.  **索引本质**：B+Tree，目的是减少 IO 次数。
2.  **设计原则**：
    *   主键自增，避免 UUID。
    *   字段类型越小越好。
    *   联合索引遵循最左前缀，高选择性在前。
    *   尽量使用覆盖索引，避免回表。
3.  **避坑指南**：
    *   避免在索引列上做函数/计算。
    *   避免 `LIKE '%...'` 前模糊（除非覆盖索引）。
    *   避免 `OR`、`!=`、`IS NULL` 导致索引失效。
    *   深分页使用子查询优化。
4.  **调优步骤**：
    *   开启慢查询日志。
    *   使用 `EXPLAIN` 分析执行计划（重点关注 type, key, rows, Extra）。
    *   小表驱动大表。
    *   利用索引排序和分组。
    *   必要时调整缓冲区参数 (`join_buffer`, `sort_buffer`, `tmp_table`)。
