# Redis 最佳实践与实战指南 - 内容总结

## 1. Redis 架构与介质选择指引

### 1.1 架构分类
Redis 集群架构主要分为 **标准版** 和 **集群版**。

#### **标准版 (Standard Edition)**
*   **拓扑结构**：业务通过 SLB 连接后端 Redis 节点。
*   **细分类型**：
    1.  **双副本 (Master-Replica)**：
        *   主节点提供服务，备节点提供 HA（高可用）。
        *   故障自动切换（<30秒）。
        *   支持数据持久化和备份，具备同城容灾能力。
        *   *注意*：主备异步同步，切换时可能存在少量数据丢失。
    2.  **单副本**：
        *   无实时同步备节点，不提供持久化/备份。
        *   适用于纯缓存、数据可丢场景，性价比高。
        *   *注意*：故障切换后需预热缓存。
    3.  **读写分离**：
        *   通过 Proxy 将读请求分发到只读节点，写请求到主节点。
        *   适用于读多写少场景。
        *   *缺点*：只读节点数据可能滞后；故障恢复时间不承诺；非特殊需求建议直接用集群版。

#### **集群版 (Cluster Edition)**
*   **适用场景**：数据量大（最大可达 TB 级）、QPS 压力大、吞吐密集型。
*   **连接模式**：
    1.  **代理模式 (Proxy)**：
        *   请求经 Proxy 转发。
        *   优点：降低开发难度，兼容性好（解决命令不兼容问题）。
        *   缺点：轻微增加响应延时。
    2.  **直连模式 (Direct)**：
        *   Client 直连 DB 节点（Redis Cluster 协议）。
        *   优点：减少网络开销，性能更高。
        *   缺点：需 Smart Client 支持，对命令兼容性要求低。
*   **命令限制**：
    *   不支持 `SWAPDB`, `CLIENT ID`, `SORT(BY/GET)`。
    *   多 Key 命令（如 `MGET`, `DEL`）受限：Key 必须 Hash 到同一 Slot（使用 Hash Tag `{}`）。
    *   Lua 脚本限制：所有 Key 必须在同一 Slot，不支持发布订阅等。

### 1.2 选型决策树
1.  **QPS/容量低 (<32GB)** -> 选 **标准版**。
    *   数据可丢/纯缓存 -> **单副本**。
    *   数据可靠 -> **双副本**。
    *   读多写少 -> **读写分离**（慎用，推荐集群版）。
2.  **QPS/容量高** -> 选 **集群版**。
    *   代码修改成本高/兼容要求高 -> **代理模式**。
    *   新业务/追求极致性能 -> **直连模式**。
    *   数据可靠性要求 -> 选择 **双副本**。

### 1.3 存储介质选择
*   **内存型**：传统 DRAM，高性能，成本较高。
*   **持久内存型 (AEP)**：
    *   基于 Intel Optane，成本比社区版低 ~30%。
    *   每个写操作持久化，掉电不丢失。
    *   解决 AOF 性能开销，无需在性能与持久化间取舍。
*   **容量存储型 (ESSD)**：
    *   基于云盘，成本极低（社区版的 15%）。
    *   适用于温冷数据存储，大容量场景。
    *   解决 Fork 内存预留问题。

### 1.4 阿里云 vs 开源 Redis 集群对比
| 特性           | 开源 Redis Cluster                         | 阿里云 Redis/Tair                         |
| :------------- | :----------------------------------------- | :---------------------------------------- |
| **高可用探测** | Gossip 协议，无中心，慢查询易误判，收敛慢  | 中心化控制，自研多因子探活，SLA <15s      |
| **迁移平滑性** | Key 粒度迁移，大 Key 卡顿，异常需手动恢复  | Slot 粒度 Precopy，无感迁移，异常自动回滚 |
| **运维成本**   | 需额外组件，手动扩缩容                     | 系统自动运维，细粒度扩缩容                |
| **内存效率**   | 集群元数据开销大，大 Key 小 Value 浪费严重 | 内存优化，无额外巨大开销                  |

## 2. Redis 开发规范和常见问题

### 2.1 核心痛点：单线程模型 (Run-to-Completion)
*   **机制**：Redis 主线程单线程处理所有请求，无 Dispatcher/Multi-worker。
*   **风险**：慢查询（如 `KEYS`, `HGETALL`, `LRANGE`）会阻塞后续所有请求。
*   **集群版局限**：虽分散流量，但单个分片被慢查询卡住仍会影响该分片服务；跨分片命令（如 `MGET`）若访问到故障分片仍会阻塞。
*   **连接池问题**：
    *   Redis 协议 (RESP) 无 Request ID，不支持异步复用连接，必须使用连接池。
    *   慢查询导致连接无法释放，迅速耗尽连接池，引发 `"Could not get a resource from the pool"`。
    *   C10K 问题：大量 Active 连接导致性能急剧下降。

### 2.2 Redis 使用边界与建议
*   **原则**：
    *   Cache 原则：“无它也可，有它更强”，不强依赖。
    *   避免 BigKey（80% 问题的根源）。
    *   Keyspace 隔离：不同业务申请不同实例。
    *   Pub/Sub 不适合做可靠消息分发。
*   **禁止/慎用操作**：
    *   **高计算消耗**：Wildcard, 复杂 Lua, 1对N PubSub。
    *   **高网络消耗**：`KEYS` 扫全表, Huge Batch `MGET/MSET`, 大 Value, `HGETALL`/`SMEMBERS` (Big Range)。
    *   **高存储消耗**：Streaming 慢消费, BigKey。

### 2.3 常见陷阱详解
1.  **BigKey (洪水猛兽)**：
    *   导致数据倾斜（某个分片内存/CPU/网卡打满）。
    *   删除 BigKey 会阻塞主线程（Redis 4.0+ 引入 `UNLINK` 异步删除）。
    *   *建议*：拆分 Key，使用 `SCAN` 替代全量获取。
2.  **Lua 脚本**：
    *   "EVAL is evil"：编译、加载、执行耗费 CPU；整个脚本原子执行，易导致引擎挂死。
    *   *建议*：尽量用复杂数据结构或 Module 替代；若用 Lua，使用 `EVALSHA` 缓存脚本；避免循环和大操作。
3.  **KEYS 命令**：
    *   全表扫描，O(N)，数据量大必现慢查。
    *   *优化*：改为 Hash 结构，使用 `HGETALL` 或 `SCAN`。
4.  **其他危险命令**：
    *   `FLUSHALL/FLUSHDB`：数据丢失风险。
    *   `BITOP/BITSET`：设置过远 Bit 导致 OOM。
    *   Ziplist 参数：小数据量使用 ziplist 节省内存但增加 CPU，建议默认配置。

### 2.4 内存模型与 OOM
*   **内存组成**：
    *   **链路内存 (动态)**：Input/Output Buffer。Range 操作或大 Key 收发慢时激增，易致 OOM。
    *   **数据内存**：用户实际数据。
    *   **管理内存 (静态)**：Hash 表开销，Key 越多占用越大。
*   **OOM 原因**：动态内存管理失效（如限流导致请求堆积、Lua 脚本内存泄露）。
*   **工具**：使用 CloudDBA “缓存分析”功能识别 BigKey、Key 分布、过期时间合理性。

### 2.5 热 Key 分析与诊断
*   **在线实时分析**：Tair 或 Redis >=4.0，精确统计 QPS >3000 的 Key。
*   **离线分析**：`imonitor` + `redis-faina`，或审计日志。
*   **全链路诊断**：
    *   **前端**：客户端连接池满、GC、DNS、网络抖动。
    *   **后端**：Proxy 流量不均、DB 慢查询、CPU/容量瓶颈。
    *   **慢日志**：合理设置 `slowlog-log-slower-than`，避免过低影响性能。

## 3. Redis 的运维实战

### 3.1 自建 vs 云 Redis
*   **ECS 自建**：
    *   *优*：便宜，权限高。
    *   *劣*：弹性差，需专职 DBA，无专家兜底，内核无优化。
*   **云 Redis (Tair)**：
    *   *优*：开箱即用，弹性升降配，内核优化（多线程、安全加固），企业级功能（审计、细粒度监控、全球多活），7x24 专家支持。
    *   *劣*：黑盒，无最高权限。
    *   *成本*：Tair 持久内存型比自建低 30%，容量存储型低 85%。

### 3.2 阿里云 Redis 运维体系
*   **监控**：支持 5s 粒度监控，涵盖 CPU、内存、QPS、带宽、延迟、Key 数量等。
*   **账号管理**：支持读写/只读账号隔离，避免误操作。
*   **审计日志**：记录写操作，可溯源，有 5%-15% 性能损耗。
*   **备份恢复**：支持 RDB+AOF，Tair 支持 PITR（按时间点恢复，秒级精度）。

### 3.3 企业版 Tair 特性
*   **全球分布式缓存 (Global Distributed Cache)**：
    *   解决跨地域访问延迟和 DNS 漂移问题。
    *   多地多活，数据实时同步。
*   **数据闪回 (PITR)**：
    *   基于 AOF 增量归档，支持秒级恢复到任意时间点。
    *   场景：防删库跑路、游戏回档、版本降级。

## 4. Redis 高并发实战：抢购系统

### 4.1 秒杀场景特点与挑战
*   **特点**：瞬时高并发、热点数据、库存有限。
*   **策略**：层层拦截（客户端 -> CDN/LocalCache -> Redis -> DB）。
*   **扣减库存时机**：推荐 **预扣库存 + 超时释放**（结合 Quartz/消息队列）。

### 4.2 Redis 实现方案
1.  **String (INCR/DECR)**：
    *   简单计数，但无上下界保护，需 Lua 保证原子性防止负数。
2.  **List (LPOP/RPOP)**：
    *   预先生成库存令牌 List，pop 成功即得。
    *   *缺点*：内存占用大，批量扣减性能差。
3.  **Hash/Set**：
    *   用于去重（限制每人购买数量）。
    *   *注意*：避免热点 Key，需对用户 UID 进行分片映射。

### 4.3 TairString (高性能 CAS)
*   **优势**：原生支持 CAS (Compare And Set) / CAD (Compare And Delete)。
*   **功能**：
    *   `EXINCRBY`：支持上下界（如库存不为负）、过期时间、自动续期。
    *   `EXCAS`：乐观锁机制，减少网络交互（失败时返回最新 Value/Version）。
*   **对比 Lua**：TairString 模块性能更高，避免 Lua 的 CPU 开销和复杂性。

### 4.4 分布式锁
*   **基础实现**：`SET key value NX EX seconds`。
*   **问题**：锁过期但业务未执行完，导致锁被其他线程获取；原持有者执行完后误删他人锁。
*   **解决**：
    *   Value 设为唯一 ID。
    *   删除时校验 Value (CAD)。
    *   续约时校验 Value (CAS)。
    *   *注意*：Redis 分布式锁非 100% 可靠，极高可靠性场景建议 Zookeeper 或消息队列串行化。

## 5. Redis 生态

### 5.1 生态工具总览
*   **Redis-shake**：阿里自研开源工具，支持解析、备份、恢复、同步（全量+增量）。
*   **DTS (Data Transmission Service)**：
    *   迁移：不停机迁移，分钟级切换。
    *   同步：单向/双向同步（异地多活）。
    *   订阅：订阅 RDS 变更更新 Redis 缓存（解耦双写逻辑）。
*   **DBS (Database Backup Service)**：混合云备份，秒级 RPO/RTO。
*   **DMS (Data Management Service)**：
    *   数据管理、操作审计。
    *   安全协同：Key 级权限管控，变更审批。
*   **DAS (Database Autonomy Service)**：
    *   自治服务：监控大盘、巡检评分、AutoScaling（自动扩缩容）。

## 6. Redis 上下游产品联动

### 6.1 Redis + RDS (关系型数据库)
*   **角色**：Redis 作为缓存加速读取，RDS 作为持久化存储。
*   **经典架构**：
    *   **读**：查 Redis -> 命中返回；未命中查 RDS -> 写入 Redis -> 返回。
    *   **写**：先写 RDS -> 删除/更新 Redis (Cache Aside Pattern)。
    *   **会话缓存**：存储用户 Session、偏好设置。
*   **数据迁移**：MySQL 结构化数据 -> 转换为 KV 结构 -> 写入 Redis。

### 6.2 Redis + Spark (大数据)
*   **场景**：广告点击统计、热点分析。
*   **流程**：用户行为 -> Redis (实时计数/去重) -> Spark (流式计算/ETL) -> Redis (结果展示) / DB。

## 7. Redis 开发实操之春运迁徙页面

### 7.1 案例背景
模拟春运迁徙页面，展示用户位置、热门区域判断、新闻通知、热力排名。

### 7.2 数据结构设计
1.  **用户信息**：**Hash** (`USER`)。
    *   存储 UserID, Name, Position 等。
2.  **地理位置判断**：**TairGis** (`CHINA`)。
    *   利用 GIS 能力判断点是否在面内（省份）、线与面相交（经过热门区域）。
    *   API: `GIS.CONTAINS`, `GIS.INTERSECTS`。
3.  **新闻通知**：**Stream** (`NEWS`)。
    *   实时消息推送。
    *   API: `XADD` (添加), `XREVRANGE` (遍历最新消息)。
4.  **热力排名**：**Sorted Set** (`RANK`)。
    *   迁入/迁出省份排名。
    *   API: `ZADD` (添加分数), `ZREVRANGE` (倒序获取 Top N)。

### 7.3 关键功能实现
*   **轨迹漫游**：通过 TairGis 判断用户历史轨迹线段是否与“热门省份”多边形相交。
*   **电子围栏/健康码**：同理，判断是否经过疫区。
*   **消息推送**：Stream 结构保证消息的顺序性和实时性。

## 总结与建议

1.  **架构选型**：根据 QPS、容量、可靠性要求选择标准版或集群版；关注成本时考虑 Tair 持久内存/容量存储型。
2.  **开发规范**：
    *   **严禁** `KEYS`、大 Value、BigKey。
    *   **慎用** Lua、PubSub、事务。
    *   **推荐** 使用 `SCAN`、`UNLINK`、Pipeline、Tair 增强数据结构（TairString, TairGis）。
3.  **运维保障**：利用云厂商提供的监控、审计、自动扩缩容、PITR 等功能；建立全链路诊断思维。
4.  **业务场景**：
    *   缓存场景遵循 Cache Aside 模式。
    *   高并发秒杀利用 TairString CAS 或预扣库存方案。
    *   LBS 场景利用 TairGis。
    *   消息场景利用 Stream。
