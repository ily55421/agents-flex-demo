## 第1章：Kubernetes API 编程范式

### 核心论点
本章主要解决 Kubernetes 原生资源无法满足用户特定需求时的扩展性问题。核心观点是通过 Custom Resource Definition (CRD) 机制，用户可以像使用原生资源一样定义和管理自定义资源，并配合控制器实现声明式API的闭环管理。

### 关键概念/事件
-   **CRD (Custom Resource Definition)**：Kubernetes 1.7 引入的功能，允许用户自定义 Kubernetes 对象资源，扩展 API Server 的能力。
-   **自定义控制器 (Custom Controller)**：负责监听自定义资源的变化，并根据业务逻辑操作资源，使系统状态趋近于用户期望的状态（Spec）。
-   **声明式 API 扩展**：CRD 与原生资源共用 kubectl CLI、安全机制和 RBAC，实现了统一的编程范式。
-   **用例背景**：解决用户自定义资源需求多、希望聚合子资源、以及原生 APIServer 扩展复杂的问题。

### 逻辑推演/叙事脉络
本章首先从需求来源出发，指出原生 Kubernetes 资源在特定场景下的局限性以及直接扩展 APIServer 的复杂性。接着引入 CRD 作为解决方案，介绍其基本概念、引入版本及优势（如共用 CLI 和安全模型）。随后通过用例解读和操作演示，展示如何定义 CRD、增加校验和状态字段。最后从架构设计角度，阐述控制器（Controller）作为“Kubernetes 大脑”的角色，说明用户声明 CRD 后需创建对应的控制器来驱动资源达到目标状态，从而完成从需求到架构设计的完整闭环。

### 经典金句/数据
> “控制器是 Kubernetes 的大脑，负责控制大部分资源的操作。”
> “用户声明完成 CRD 后，需要创建一个控制器来操作自定义资源完成目标。”

## 第2章：K8s 的应用编排与管理：核心原理

### 核心论点
本章深入解析 Kubernetes 资源对象的结构及其背后的控制器模式。核心观点是 Kubernetes 采用声明式 API 设计，通过控制器异步地控制系统向终态（Spec）趋近，实现了自动化和无人值守的管理能力。

### 关键概念/事件
-   **资源元信息 (Metadata)**：包括 Labels（标识型，用于筛选和组合）、Annotations（非标识性，存储扩展信息）和 OwnerReference（用于级联删除和反向查找）。
-   **Spec 与 Status**：Spec 代表期望状态，Status 代表观测到的状态，控制器的目标是消除两者之间的差异。
-   **控制器模式 (Controller Pattern)**：包含 Reflector、Informer、Indexer、Workqueue 等组件，通过 List & Watch 机制监听变化，并将事件放入工作队列异步处理。
-   **声明式 vs 命令式**：声明式 API 天然记录状态、支持幂等操作、可合并变更，优于命令式交互的复杂性和并发问题。

### 逻辑推演/叙事脉络
本章首先拆解 Kubernetes 资源对象的核心组成部分，重点讲解 Labels、Annotations 和 OwnerReference 的作用及区别。随后深入探讨控制器模式，详细描绘了从 API Server 到 Informer、再到 Workqueue 和 Worker 的数据流转过程，并以 ReplicaSet 扩容为例，演示了控制器如何感知变化、入队、处理并更新状态。最后对比命令式与声明式 API 设计的优劣，总结控制器模式如何通过异步驱动实现系统的自动化运维，并引出 Operator 作为扩展手段的重要性。

### 经典金句/数据
> “控制器模式总结：由声明式的 API 驱动 – K8S 资源对象；由控制器异步地控制系统向终态驱近。”
> “声明式 API：天然地记录了状态；幂等操作、可在任意时刻反复操做；正常操作即巡检；可合并多个变更。”

## 第3章：Kata Containers 创始人带你入门安全容器技术

### 核心论点
本章探讨云原生语境下的安全容器技术，旨在解决传统容器共享宿主内核带来的安全风险。核心观点是通过引入间接层（如虚拟机或进程级虚拟化），将应用执行与宿主机隔离，从而在保持容器体验的同时提供更强的安全隔离。

### 关键概念/事件
-   **安全容器 (Secure Container)**：为容器应用提供完整 OS 执行环境，但通过隔离层避免应用直接访问主机资源。
-   **Kata Containers**：基于虚拟化的安全容器方案，使用轻量级 VM 作为 Pod Sandbox，Guest 内核独立于 Host 内核。
-   **gVisor**：基于进程级虚拟化的安全容器方案，通过拦截系统调用并在用户态模拟内核行为（Sentry/Gofer）来实现隔离。
-   **间接层 (Indirection Layer)**：安全容器的精髓，允许 Bug 发生但通过隔离层阻挡其影响，符合 Linus Torvalds 的安全理念。

### 逻辑推演/叙事脉络
本章从“命名”难题切入，界定云原生语境下“应用容器”与“安全容器”的区别。接着阐述安全问题的本质在于隔离，引入“间接层”概念。随后分别详细介绍两种主流实现：Kata Containers（利用 VM 实现强隔离，符合 OCI 规范，支持动态资源调整）和 gVisor（通过 syscall interception 实现进程级隔离）。最后对比两者架构差异，并展望安全容器在降低开销、提升效能方面的潜力，提出关于未来统一技术和硬件改进的思考。

### 经典金句/数据
> “安全问题的唯一正解在于允许那些（导致安全问题的）Bug 发生，但通过额外的隔离层来阻挡住它们。” —— Linus Torvalds
> “安全容器不仅仅是在做安全隔离……将来的安全容器，可能不仅是隔离性开销的降低，甚至是提升应用的效能。”

## 第4章：Kubernetes API 编程利器：Operator 和 Operator Framework

### 核心论点
本章介绍如何利用 Operator 模式管理和部署复杂的 Kubernetes 应用。核心观点是 Operator = CRD + Webhook + Controller，而 Operator Framework（如 Kubebuilder）提供了标准化的脚手架和运行时库，极大简化了 Operator 的开发流程。

### 关键概念/事件
-   **Operator 组成**：CRD（定义资源）、Webhook（校验和突变）、Controller（协调逻辑）。
-   **Operator Framework**：包括 Kubebuilder 和 Operator SDK，基于 controller-runtime 和 controller-tools，提供代码生成、测试和部署支持。
-   **Webhook 类型**：Mutating Webhook（修改传入对象，如注入默认值）和 Validating Webhook（校验对象合法性）。
-   **Reconcile 循环**：Controller 的核心逻辑，不断获取当前状态，计算差异，执行操作，并更新 Status。

### 逻辑推演/叙事脉络
本章首先概述 Operator 的基本概念和工作模式，明确其由 CRD、Webhook 和 Controller 构成。接着介绍主流的 Operator Framework 项目（Kubebuilder 和 Operator SDK）及其异同。随后通过一个 SidecarSet 的实战案例，分步骤演示如何使用 Kubebuilder 初始化项目、创建 API（CRD）、填充 CRD 结构、生成并填充 Webhook 逻辑、以及实现 Controller 的 Reconcile 函数。最后总结 Operator 的工作流程，强调框架如何帮助开发者聚焦于业务逻辑而非底层基础设施。

### 经典金句/数据
> “Operator：operator 是描述、部署和管理 kubernetes 应用的一套机制，从实现上来说，operator= CRD+ webhook+ controller。”
> “开发人员仅需关心被管理应用的运维逻辑实现。”

## 第5章：K8s 安全之访问控制

### 核心论点
本章系统讲解 Kubernetes 的访问控制体系，涵盖认证、鉴权和准入控制三个环节。核心观点是通过 RBAC、Service Account 和 Pod Security Policy 等机制，遵循最小权限原则，实现多租户环境下的安全隔离和合规管理。

### 关键概念/事件
-   **访问控制三阶段**：Authentication（认证，确认身份）、Authorization（鉴权，确认权限，如 RBAC）、Admission Control（准入控制，确认合规，如 PSP）。
-   **RBAC (Role-Based Access Control)**：基于角色、主体（User/Group/SA）、动词（Verb）和资源（Resource）的权限模型，包括 Role/ClusterRole 和 RoleBinding/ClusterRoleBinding。
-   **Service Account**：Pod 内部进程访问 APIServer 的身份凭证，自动挂载 Token。
-   **Pod Security Policy (PSP)**：通过准入控制器强制 Pod 满足安全标准（如非 Root 运行、只读文件系统），防止特权逃逸。

### 逻辑推演/叙事脉络
本章首先构建 Kubernetes API 请求的安全模型，明确“谁在何种条件下对什么资源做什么操作”。接着详细拆解认证机制，包括 X509 证书、Bearer Token 和 Service Account 的使用与配置。随后深入讲解 RBAC 模型，区分 Namespace 级别的 Role 和集群级别的 ClusterRole，并说明绑定关系。最后探讨运行时安全，介绍 Security Context 的设置和 Pod Security Policy 的应用，强调通过多层防御（RBAC + PSP + NetworkPolicy 等）实现多租户安全加固。

### 经典金句/数据
> “Kubernetes 没有自身的用户管理能力……Kubernetes 中的用户通常是通过请求凭证设置。”
> “遵循权限最小化原则……在应用运行时刻遵循权限的最小化原则，尽可能缩小 pod 内容器的系统权限。”

## 第1章：应用编排与管理 - Deployment
**来源文件**：【应用编排与管理 - Deployment】+曾凡松（逐灵）+2019.9.26.pdf

### 核心论点
- **问题**：直接管理集群中所有Pod无法解决可用数量保证、镜像版本更新、更新过程中的服务可用性及快速回滚等问题。
- **观点**：Deployment作为管理部署发布的控制器，通过定义Pod期望数量、配置发布策略及支持一键回滚，实现了应用的声明式管理与平滑升级。

### 关键概念/事件
- **Deployment控制器**：负责维持Pod数量与期望一致，按策略更新Pod，保证更新过程中不可用Pod数量在限定范围内，并支持回滚。
- **ReplicaSet**：Deployment实际管理的对象，每个ReplicaSet对应Deployment template的一个版本，负责维持Pod副本数。
- **滚动更新策略**：通过`MaxUnavailable`（最多不可用Pod数）和`MaxSurge`（最多超出期望Pod数控制升级过程中的Pod数量变化。
- **版本回滚**：利用`revisionHistoryLimit`保留历史ReplicaSet，支持回滚到上一个版本或指定版本。

### 逻辑推演/叙事脉络
本章首先提出直接管理Pod面临的四大痛点（数量、更新、可用性、回滚），引出Deployment的概念。接着通过Nginx部署案例，解析Deployment YAML语法（replicas, template, selector等）及状态查看方法（DESIRED, CURRENT等）。随后深入架构设计，阐明Deployment并不直接管理Pod，而是通过管理不同版本的ReplicaSet来间接管理Pod，详细演示了扩容、发布（滚动更新）和回滚的内部机制。最后解析了关键字段如`MinReadySeconds`、`progressDeadlineSeconds`及升级策略参数。

### 经典金句/数据
> “Deployment只负责管理不同版本的ReplicaSet，由ReplicaSet管理Pod副本数。”

> “回滚的过程，其实是Deployment controller重新调整下属ReplicaSet的replicas数量，最终使旧版本的ReplicaSet重新扩出所有Pod。”

## 第2章：应用编排与管理 - Job & DaemonSet
**来源文件**：【应用编排与管理：Job&DaemonSet】+陈显鹭+2019.10.8.pdf

### 核心论点
- **问题**：普通Pod无法保证任务进程正确结束、失败重试、依赖管理及并行度控制；也无法保证每个节点运行相同Pod及节点变动时的自动适配。
- **观点**：Job控制器用于管理一次性任务，确保指定数量的Pod成功终止；DaemonSet控制器用于守护进程，保证集群内每个（或部分）节点运行一组相同的Pod。

### 关键概念/事件
- **Job**：管理任务的控制器，支持设置`completions`（完成次数）、`parallelism`（并行度）和`backoffLimit`（重试限制），适用于批处理任务。
- **CronJob**：基于时间调度的Job，使用crontab格式，支持`concurrencyPolicy`（并发策略）和历史记录限制。
- **DaemonSet**：守护进程控制器，适用于日志收集（Fluentd）、监控代理等场景，保证新节点加入时自动部署Pod，节点移除时自动清理。
- **更新策略**：DaemonSet支持`RollingUpdate`（默认，滚动更新）和`OnDelete`（手动删除后更新）两种升级方式。

### 逻辑推演/叙事脉络
本章分为两部分。第一部分针对批处理任务，指出直接运行Pod的缺陷，引入Job控制器，通过Pi计算案例讲解Job语法、状态查看及并行执行机制，并延伸至CronJob定时任务。第二部分针对节点级服务，提出在每个节点运行相同Pod的需求，引入DaemonSet，以Fluentd为例展示其语法、状态及在节点增删时的行为，最后对比了两种更新策略的差异。

### 经典金句/数据
> “Job Controller负责根据配置创建Pod，跟踪Job状态，根据配置及时重试Pod或者继续创建。”

> “DaemonSet Controller会自动添加affinity & label来跟踪对应的pod，并根据配置在每个节点或者适合的部分节点创建Pod。”

## 第3章：应用存储和持久化数据卷 - 核心知识
**来源文件**：【应用存储和持久化数据卷 - 核心知识】+至天+2019.10.9.pdf

### 核心论点
- **问题**：Pod Volumes生命周期与Pod绑定，导致数据在Pod重建或迁移时丢失，且难以实现存储与计算的解耦及复用。
- **观点**：通过PV（PersistentVolume）和PVC（PersistentVolumeClaim）体系将存储与计算分离，PVC作为用户接口抽象存储需求，PV作为实现承载具体存储信息，支持静态和动态供给。

### 关键概念/事件
- **Pod Volumes**：包括emptyDir、hostPath等，生命周期随Pod，适用于临时数据或同Pod内容器共享，但不具备持久化和跨Pod共享能力。
- **PV与PVC**：PV是集群中的存储资源对象，PVC是用户对存储的请求。两者通过`AccessModes`、`Capacity`等匹配绑定，实现解耦。
- **StorageClass**：动态供给的核心，作为创建PV的模板。用户只需在PVC中指定StorageClass，Kubernetes即可自动创建对应的PV。
- **Reclaim Policy**：PV释放后的处理策略，包括Retain（保留，需管理员手动处理）、Delete（删除存储资产）和Recycle（已废弃）。

### 逻辑推演/叙事脉络
本章从Pod数据持久化的痛点出发，介绍本地和网络存储类型，指出Pod Volumes的局限性。随后引入PV/PVC体系，解释其设计意图（职责分离、简化用户操作）。接着对比静态供给（管理员预创建PV）和动态供给（通过StorageClass自动创建PV）两种模式，并以阿里云NAS和云盘为例展示配置方法。最后详细解析PV的状态流转（Available -> Bound -> Released -> Deleted/Failed）及关键字段。

### 经典金句/数据
> “PVC像是面向对象编程中抽象出来的接口，PV是接口对应的实现。”

> “到达released状态的PV无法根据Reclaim Policy回到available状态而再次bound新的PVC。”

## 第4章：应用存储和持久化数据卷 - 存储快照与拓扑调度
**来源文件**：【应用存储和持久化数据卷 - 存储快照与拓扑调度】+至天+2019.11.4.pdf

### 核心论点
- **问题**：重要数据误操作后难以恢复；特定存储（如Local PV、云盘）对节点位置有依赖，而Pod调度与PV创建/绑定的分离可能导致Pod被调度到无法访问PV的节点。
- **观点**：引入Volume Snapshot实现数据备份与恢复；引入拓扑感知调度（Topology-Aware Scheduling），通过延迟绑定（WaitForFirstConsumer）确保Pod调度到满足PV拓扑限制的节点后再进行PV绑定或创建。

### 关键概念/事件
- **Volume Snapshot**：包含VolumeSnapshotClass、VolumeSnapshot和VolumeSnapshotContent三个对象，支持从PVC创建快照，并从快照恢复数据到新PVC。
- **拓扑域（Topology）**：通过Node Label标识节点位置（如Zone、Rack），PV可通过`nodeAffinity`限制访问节点。
- **延迟绑定（Delayed Binding）**：StorageClass中设置`volumeBindingMode: WaitForFirstConsumer`，使PV的绑定或动态创建推迟到Pod调度确定节点后进行。
- **AllowedTopologies**：在StorageClass中指定允许创建PV的拓扑区域，指导动态供给时在正确的区域创建存储。

### 逻辑推演/叙事脉络
本章首先介绍存储快照的背景与对象模型，展示如何通过Snapshot备份和恢复数据。随后重点讨论存储拓扑调度问题，分析Local PV和多Zone云盘场景下，因PV访问限制与Pod调度分离导致的启动失败问题。提出解决方案：改进Scheduler和PV Controller，支持延迟绑定。详细阐述了调度流程：Scheduler在预选节点时检查PV的NodeAffinity或StorageClass的AllowedTopologies，选定节点后才触发PV绑定或创建，确保存储可访问性。

## 第5章：有状态应用编排 - StatefulSet
**来源文件**：【有状态应用编排：StatefulSet】+酒祝+2020.2.10.pdf

### 核心论点
- **问题**：Deployment管理的Pod是无序、对等的，无法满足有状态应用对稳定网络标识、稳定存储标识、有序部署/扩展及有序删除的需求。
- **观点**：StatefulSet通过为每个Pod分配唯一序号、配合Headless Service提供稳定网络标识、通过VolumeClaimTemplates提供独立存储，并支持有序的管理策略，专门用于编排有状态应用。

### 关键概念/事件
- **稳定标识**：Pod名称格式为`<statefulset-name>-<ordinal>`，序号从0开始。配合Headless Service，每个Pod拥有唯一的DNS记录。
- **VolumeClaimTemplates**：StatefulSet为每个Pod实例创建独立的PVC，即使Pod重建，也会复用原有的PVC，保证数据持久性。
- **有序管理**：默认策略`OrderedReady`下，扩容、缩容、更新均按序号顺序执行（如扩容0->1->2，缩容2->1->0，更新2->1->0）。
- **更新策略**：支持`RollingUpdate`和`OnDelete`。RollingUpdate可通过`partition`字段控制灰度发布，仅更新序号大于等于partition的Pod。

### 逻辑推演/叙事脉络
本章回顾Deployment的无状态特性，引出有状态应用的四大需求（独立标识、稳定网络、独立存储、有序操作）。介绍StatefulSet如何通过这些特性满足需求，并通过Nginx StatefulSet案例展示Service、Pod、PVC的状态及关系。深入架构设计，说明StatefulSet直接管理Pod并使用ControllerRevision管理版本。详细模拟了扩容、缩容和发布过程，强调其有序性和存储复用特性。最后解析了`podManagementPolicy`和`updateStrategy`等关键配置。

### 经典金句/数据
> “不同于Deployment使用ReplicaSet来管理版本和维持副本数，StatefulSet controller直接管理下属的Pod，而Pod中用一个label来标识版本：controller-revision-hash。”

> “扩容时，必须前面序号的Pod都ready了，才能扩下一个；缩容时，按照倒序删除。”

## 第1部分：容器基本概念

### 核心论点
- **问题**：什么是容器？它与虚拟机（VM）有何本质区别？容器是如何构建和运行的？
- **观点**：容器是视图隔离、资源可限制、独立文件系统的进程集合；其核心优势在于轻量级启动和资源高效利用，通过镜像实现“Build once, Run anywhere”。

### 关键概念/事件
- **容器（Container）**：一种进程级别的隔离技术，通过 Namespace 实现视图隔离，通过 Cgroup 实现资源限制，通过 Chroot/UnionFS 实现独立文件系统。
- **镜像（Image）**：运行容器所需的所有文件集合，采用分层结构（Changeset），类似磁盘快照，提高分发效率。
- **Dockerfile**：描述镜像构建步骤脚本，通过 `docker build` 生成镜像。
- **容器生命周期**：遵循单进程模型，Init 进程生命周期即容器生命周期；支持 exec 进入运维；数据持久化需通过 Volume 实现，独立于容器生命周期。
- **Moby 架构**：包含 Moby Daemon、Containerd（运行时管理引擎）、Shim（生命周期管理）以及底层运行时（runC/kata/gVisor）。

### 逻辑推演/叙事脉络
本章首先定义容器的本质，对比传统 VM 架构，指出容器共享 Host OS Kernel，无 Guest OS，因此启动更快、资源消耗更少但隔离性弱于 VM。接着介绍镜像的分层构建原理及 Docker Registry 的分发机制。随后阐述容器的生命周期管理，强调单进程模型和数据持久化的特殊性。最后解析 Moby 引擎架构，展示从 Daemon 到 Shim 再到 OCI 运行时的调用链，为后续深入理解容器运行时打下基础。

### 经典金句/数据

## 第2部分：如何实现应用配置管理？

### 核心论点
- **问题**：在不可变基础设施（容器镜像）背景下，如何解决可变配置、敏感信息存储、身份认证、资源限制及安全管控等问题？
- **观点**：Kubernetes 通过 ConfigMap、Secret、ServiceAccount、Resource Quotas、SecurityContext 和 InitContainer 等资源对象，实现了配置与镜像解耦、敏感信息安全存储及细粒度的运行时控制。

### 关键概念/事件
- **ConfigMap**：管理非敏感配置（环境变量、配置文件、命令行参数），实现配置与镜像解耦。限制：大小不超过 1MB，Pod 只能引用同 Namespace 下的 ConfigMap。
- **Secret**：存储敏感信息（密码、Token），采用 Base64 编码（非加密，需注意权限控制）。类型包括 Opaque、ServiceAccount Token、Docker Config 等。
- **ServiceAccount**：解决 Pod 在集群内的身份认证问题，通过自动挂载 Secret（Token）实现 API Server 访问认证，配合 RBAC 进行授权。
- **Resource（资源配置）**：通过 Requests/Limits 管理 CPU/Memory/Ephemeral Storage，决定 Pod 的 QoS 等级（Guaranteed/Burstable/BestEffort），影响驱逐优先级。
- **SecurityContext**：控制容器行为安全，包括用户ID、SELinux、Privileged 模式、Capabilities、AppArmor、Seccomp 等。
- **InitContainer**：在普通容器启动前按序执行，用于初始化或前置条件校验，执行成功后退出。

### 逻辑推演/叙事脉络
本章从 Pod 面临的六大配置管理需求出发，逐一介绍 Kubernetes 提供的解决方案。首先介绍 ConfigMap 处理可变配置，强调其与镜像解耦的价值及使用限制；接着引入 Secret 处理敏感信息，指出其编码而非加密的特性及最佳实践；随后讲解 ServiceAccount 如何实现 Pod 身份认证；再深入资源限制（Requests/Limits）对 QoS 和调度的影响；接着探讨 SecurityContext 对运行时安全的管控；最后介绍 InitContainer 在启动流程中的特殊作用。整体逻辑围绕“配置-安全-资源-启动”展开。

### 经典金句/数据

> “Secret 虽然采用 base-64 编码，但是可以简单解码查看原始信息。因此机密信息采用 Secret 存储仍需要慎重考虑或者 Secret 访问者进行控制。”

## 第3部分：深入剖析 Linux 容器

### 核心论点
- **问题**：Linux 容器底层是如何实现隔离和资源限制的？容器镜像的文件系统如何工作？
- **观点**：容器技术核心依赖 Linux Kernel 的 Namespace（隔离）和 Cgroup（限制）；镜像基于联合文件系统（UnionFS）实现分层复用；containerd 通过 Shim 进程解耦运行时管理，遵循 OCI 标准。

### 关键概念/事件
- **Namespace**：提供视图隔离，包括 Mount、UTS、PID、Network、User、IPC 等 6 种常见类型，使进程看到独立的系统视图。
- **Cgroup**：提供资源限制，包括 CPU、Memory、Device、Blkio、PID 等子系统，控制进程组资源使用上限。
- **OverlayFS**：容器文件系统实现，由 Lower（只读镜像层）、Upper（可写容器层）、Workdir（中间层）和 Merged（合并视图）组成。写时复制（Copy-on-Write）机制优化性能。
- **OCI 标准**：Open Container Initiative，定义 Runtime Spec 和 Image Spec，确保容器格式和运行时的互操作性。
- **Containerd 架构**：包含 containerd-shim-v1/v2，负责管理容器生命周期，即使 containerd 重启也不影响容器运行，支持多种运行时（runc, gvisor, kata）。

### 逻辑推演/叙事脉络
本章深入 Linux 内核层面，首先解析 Namespace 和 Cgroup 两大基石，说明它们如何分别实现隔离和资源控制，并列举常用类型。接着详细剖析 Docker 镜像的底层实现——OverlayFS，解释分层结构、读写机制（Copy-on-Write）及删除操作原理（Whiteout）。最后介绍容器引擎架构演进，重点讲解 containerd 及其 Shim 进程的作用，强调 OCI 标准在解耦上层编排与底层运行时中的关键地位。

### 经典金句/数据
> “以 docker 为例 cgroup + namespace + docker image”
> “写：容器创建出来时，upper 层是空的，只有对文件进行写操作时，才会从 lower 层拷贝文件上来，对副本进行操作”

## 第4部分：手把手带你理解 etcd

### 核心论点
- **问题**：etcd 是什么？它如何保证分布式系统的数据一致性和高可用性？在 Kubernetes 中扮演什么角色？
- **观点**：etcd 是基于 Raft 协议的高可用、强一致 Key-Value 存储系统，通过 MVCC、Watch、Lease 等机制支撑 Kubernetes 的元数据存储、服务发现及分布式协调。

### 关键概念/事件
- **Raft 共识算法**：etcd 核心一致性协议，通过 Leader/Follower 角色选举和日志复制实现强一致；容忍 (N-1)/2 个节点故障。
- **MVCC（多版本并发控制）**：每个 Key 维护多个版本，通过 Revision 标识全局单调递增版本号，支持历史版本查询和并发控制。
- **Watch 机制**：客户端可监听 Key 变化，etcd 通过 Streaming 方式推送事件，实现配置动态更新和服务发现。
- **Lease（租约）**：关联 Key 的生命周期，通过 KeepAlive 维持，超时自动删除，用于实现服务注册健康检测和分布式锁。
- **典型场景**：Kubernetes 元数据存储（Pods/ConfigMaps等）、服务发现（Service Discovery）、分布式选主（Leader Election）、分布式协调信号量。

### 逻辑推演/叙事脉络
本章首先回顾 etcd 发展历程及其在 CNCF 中的地位。接着深入架构内部，解析 Raft 协议如何保证一致性，以及 WAL、BoltDB、Snapshot 等组件的作用。随后详细介绍 etcd 的核心 API 特性：MVCC 版本控制、Watch 监听机制、Lease 租约管理及事务支持。最后结合 Kubernetes 实际场景，阐述 etcd 在元数据存储、服务发现和分布式协调（如选主）中的具体应用，体现其作为分布式系统“基石”的价值。

### 经典金句/数据
> “A distributed, reliable key-value store for the most critical data of a distributed system”
> “3个节点容忍1个故障，5个节点容忍2个故障”

## 第5部分：理解容器运行时接口 CRI

### 核心论点
- **问题**：Kubernetes 为何引入 CRI？CRI 如何解决 Kubelet 与容器运行时耦合的问题？
- **观点**：CRI（Container Runtime Interface）通过 gRPC 协议抽象 Pod 级别接口，解耦 Kubelet 与具体容器运行时（如 Docker、containerd、CRI-O），降低维护复杂度并提升扩展性。

### 关键概念/事件
- **CRI 由来**：K8s v1.5 之前，Kubelet 内嵌 dockershim 等操作特定运行时代码，导致维护复杂且难以扩展新运行时（如 rkt, hyper.sh）。
- **CRI 设计**：定义了一套 Pod 级别的容器接口，通过 gRPC 协议通信，性能优于 HTTP/REST。
- **CRI 实现**：包括 cri-containerd（后演进为 containerd 插件）、CRI-O（直接基于 OCI）、PouchContainer 等。
- **cri-tools**：官方提供的调试和测试工具集，包含 crictl（类 docker 命令行）和 critest（一致性测试工具）。
- **架构演进**：引入 CRI 后，Kubelet 不再直接依赖 Docker Daemon，而是通过 CRI Shim 与符合标准的运行时交互。

### 逻辑推演/叙事脉络
本章首先回顾 CRI 引入前的背景，指出 Kubelet 内嵌运行时代码带来的维护痛点和扩展瓶颈。接着介绍 CRI 的设计目标：通过 gRPC 抽象接口实现解耦。随后列举主流 CRI 实现方案（cri-containerd, CRI-O 等），并简要分析其特点。最后介绍 cri-tools 工具集，帮助用户调试和验证 CRI 兼容性，并以思考题结尾，探讨 CRI 规范的未来完善方向。

### 经典金句/数据
> “抽象一套 POD 级别的容器接口，解耦 Kubelet 与容器运行时”
> “gRPC 性能优于 http/REST 模式”

## 第1章：超大规模商用 K8s 场景下，阿里巴巴如何动态解决容器资源的按需分配问题？

### 核心论点
- **主要问题**：在超大规模集群中，如何平衡应用稳定性（SLA）与资源利用率，解决因资源初始分配不合理导致的 OOM、CPU Throttle 及应用 Crash 问题。
- **核心观点**：通过轻量级的、不侵入 K8s 核心组件的动态资源边界调整机制（采集-画像-策略），实现业务容器资源的按需分配，既要稳定性也要利用率。

### 关键概念/事件
- **资源竞争根源**：无人知晓如何配置合适的初始资源值，导致离线与在线应用混部时产生资源争抢，关键应用在流量峰值时因资源不足性能断崖式下跌。
- **潮汐应用与分时复用**：利用在线（延时敏感、高优先级）与离线（延时不敏感、低优先级）应用的互补性，通过错峰使用资源提高整体利用率。
- **动态调整架构**：由 Data Collector（数据采集）、Data Aggregator（容器画像）、Policy Engine（资源调整策略）组成，以 DaemonSet 形式部署，开销小且具备自愈能力。
- **资源调整手段**：基于 Cgroup 数据，动态调整 CPU Share/Quota/Cpuset 和 Memory Limit/Swap，以及在高压下抑制低优先级 Pod。

### 逻辑推演/叙事脉络
本章首先指出阿里巴巴面临的海量应用与节点带来的调度与稳定性挑战，特别是资源初始分配不合理引发的生产事故。接着分析了根源：静态配置无法适应动态负载，且为了峰值预留过多资源造成巨大浪费。随后提出解决方案：构建一个轻量级、插件化的动态资源调整系统。该系统通过实时采集监控数据，形成容器画像，并由策略引擎根据 SLA（如延迟 P95 ≤ 250ms）动态调整 Cgroup 参数。最后展示了该方案在低负载和高负载下的调整效果，并展望了与 HPA/VPA 联动及开源计划（OpenKruise）。

## 第2章：为你写诗：3 步搭建 Serverless AI 应用

### 核心论点
- **主要问题**：传统自建 AI 推理服务面临基础设施管理复杂、弹性伸缩慢、运维成本高等痛点。
- **核心观点**：利用阿里云函数计算（FC）的免运维、毫秒级弹性伸缩特性，结合 Funcraft 工具，可以极简地构建高可用、低成本的 Serverless AI 应用，并通过预留模式解决冷启动问题。

### 关键概念/事件
- **Serverless AI 工作流**：数据处理 -> 模型训练 -> 模型部署。函数计算专注于“模型部署”与“推理响应”环节。
- **三步搭建法**：① `git clone` 代码；② `fun install` 安装依赖；③ `fun deploy` 一键部署。无需关心底层 ECS、SLB 配置。
- **冷启动优化**：通过“预留模式”（Pre-reserved Instances）预启动实例，将延迟控制在百毫秒级别，避免按需调用时的秒级延迟毛刺。
- **成本优势对比**：在特定负载模型下（如按需付费占比 <20%），函数计算组合付费模式相比按峰值预留 ECS 或弹性伸缩方案，具有显著的成本优势且无需支付 SLB 费用。

### 逻辑推演/叙事脉络

## 第3章：备战双 11！蚂蚁金服万级规模 K8s 集群管理系统如何设计？

### 核心论点
- **主要问题**：在万级节点、十万级 Pod 的超大规模集群中，如何实现集群全生命周期管理、故障自愈以及变更的可控性。
- **核心观点**：采用声明式（Declarative）设计理念，通过 Operator 模式将集群、节点、组件等抽象为 CRD，利用“观察-分析-行动”闭环实现自动化管理与故障自愈。

### 关键概念/事件
- **声明式 vs 命令式**：从“告诉系统怎么做（How）”转变为“告诉系统最终状态是什么（What）”，由控制器负责弥合当前状态与期望状态的差异。
- **Cluster-Operator**：负责集群级别的 lifecycle 管理（创建、删除、升级），通过 Cluster CRD 定义集群期望状态。
- **Machine-Operator**：负责节点级别的管理，包括 OS/内核补丁、Docker/Kubelet 安装升级、节点终态管理及故障自愈。引入 ReadinessGates 确保节点就绪后再调度。
- **故障自愈体系**：基于 Event Center（发布/订阅模式），由 Fault Detector 检测硬件或组件故障，触发 Recovery Operators 执行隔离（Taint/Evict）、修复（重装 OS/组件恢复）等操作。
- **风险防控**：在自动化操作中引入风险评估、限流（Rate Limiting）和熔断（Circuit-Breaker）机制，防止雪崩效应。

### 逻辑推演/叙事脉络
本章首先介绍了蚂蚁金服集群的庞大规模及其带来的管理挑战（生命周期、故障恢复、变更控制）。接着阐述了核心设计概念：从命令式向声明式转变，强调 Self-recovery（自愈）能力。随后详细拆解了两大核心 Operator：Cluster-Operator 处理集群维度，Machine-Operator 处理节点维度（含 ReadinessGates 机制）。重点介绍了基于 Event Center 的故障自愈流程：检测->发布事件->订阅恢复->执行操作（隔离/修复）。最后强调了在大规模自动化运维中必须配套的风险防控机制（限流、熔断），确保双 11 等高峰期的稳定性。

### 经典金句/数据
- **Declarative**: "Tell What, Not How."
- **Self-recovery Loop**: "Observe (watch actual state) -> Analyze (difference from desired and actual state) -> Action (change to desired state)."
- **规模数据**: "Tens of thousands of nodes in one cluster", "Hundreds of thousands of pods".

## 第4章：阿里云如何基于标准 K8s 打造边缘计算云原生基础设施

### 核心论点
- **主要问题**：边缘计算场景面临云边协同标准缺失、网络不可靠、资源异构且受限、安全风险高等挑战，如何将云原生能力延伸至边缘。
- **核心观点**：基于标准 Kubernetes，通过“云管边”架构、边缘自治、Edge Unit（边缘单元）及轻量化改造，构建“云-边-端”一体化的云原生基础设施，实现统一管控与边缘高可用。

### 关键概念/事件
- **云边端一体**：“云”为中心管控，“边”为靠近数据的计算资源，“端”为 IoT 设备。目标是降低时延、减轻云端压力、降低带宽成本。
- **边缘自治（Edge Autonomy）**：在云边断网情况下，通过 Edge-hub 缓存云端数据，保障边缘业务连续性；保持 Pod IP 和 Flannel VTEP MAC 地址不变，确保本地服务稳定。
- **云边双向通道**：针对边缘节点无公网 IP 的问题，建立反向通道（WebSocket 等），使云端 APIServer 和 MetricServer 能按需中转请求，实现原生运维支持。
- **Edge Unit (EU)**：将边缘节点划分为独立的逻辑单元（如 CDN 机房、工厂园区），EU 内网络闭环，EU 间通过 Service/Ingress 通信，避免跨 EU 的 Pod 网络直连，简化网络模型。
- **轻量化改造**：针对 IoT 极致资源约束，使用 containerd 替代 Docker，裁剪 Kubelet 功能，减少 Sidecar 开销，适配异构硬件。

### 逻辑推演/叙事脉络
本章首先定义了云原生与边缘计算的概念，指出“云边端协同”的价值与挑战。接着提出基于标准 K8s 的解决方案：将 K8s 管控面托管在云端，利用云厂商能力降低复杂度。随后详细阐述了关键技术点：1. **边缘自治**，解决断网存活问题；2. **反向通道**，解决运维可达性问题；3. **Edge Unit**，通过单元化部署解决网络异构与调度亲和性问题。此外，特别强调了针对 IoT 场景的**轻量化**必要性。最后通过优酷筋斗云（降低延迟、节省成本）、CDN PaaS 等案例，验证了 ACK@Edge 在实际业务中的价值。

### 经典金句/数据
> “Kubernetes——让容器应用进入大规模工业生产，已然成了容器编排系统的事实标准。”
> “30%的用户希望在边缘部署完整的 Kubernetes 集群，而 70%的用户希望在云端部署 Kubernetes 的管理面并且在边缘节点上只部署 Kubernetes 的 agent。”
> **案例数据**：基于 ACK@Edge 的优酷筋斗云，“端到端延迟降低 75%，机器成本节省 50%”。
