# 文档博客 Python Web 服务 v1.3 优化迭代方案

> 分析日期：2026-05-26  
> 分析范围：`web-app/server.py`、`web-app/config.json`、`web-app/static/`、`web-app/test_api.py`、`web-app/test_management.py`、既有 `docs/v1.1` 与 `docs/v1.2` 优化文档  
> 定位：在保持“零外部依赖、本地轻量运行”优势的前提下，优先补齐服务端安全、数据一致性、测试隔离和运维可观测能力。

---

## 1. 当前服务概览

### 1.1 技术栈与运行方式

| 模块 | 当前实现 |
|------|----------|
| Web 服务 | Python 标准库 `http.server.HTTPServer` + `SimpleHTTPRequestHandler` |
| 数据库 | SQLite，启用 WAL 与外键 |
| 全文检索 | SQLite FTS5，`trigram` tokenizer，支持中文子串匹配 |
| 静态资源 | 自定义 `_serve_static()`，提供 ETag 与 Cache-Control |
| 前端 | 原生 HTML/CSS/ES Module，Hash Router |
| PWA | 已有 `manifest.json` 与 `sw.js`，静态资源缓存与 API Network-First |
| 本地状态 | `localStorage`，封装于 `static/js/storage.js` |
| 测试 | 两个脚本式 HTTP 测试文件，依赖本地 8080 服务和真实数据库 |

### 1.2 已具备能力

1. 文档导入与索引：启动时全量或增量扫描 Markdown，写入 `documents` 与 `docs_fts`。
2. 分类体系：内置 16 类规则，按文件名与内容预览自动分类。
3. 搜索能力：基础全文搜索、搜索建议、分类过滤、摘要片段。
4. 阅读能力：文章详情、目录、代码高亮、阅读模式、字体调节、阅读进度。
5. 管理能力：收藏、标签、回收站、批量改分类。
6. 关联能力：相似文档推荐、知识图谱接口与 Canvas 可视化。
7. 观测能力：健康检查、前端错误上报、前端性能指标上报、请求统计。
8. 离线能力：Service Worker 缓存静态资源，API 失败时返回缓存或离线 JSON。

### 1.3 版本状态判断

既有 `docs/v1.2-优化方案.md` 中规划的多项能力已经部分落地，包括 PWA、阅读模式、前端错误监控、性能指标、标签、回收站、知识图谱等。但代码与文档版本存在漂移：

| 位置 | 状态 |
|------|------|
| `docs/v1.2-优化方案.md` | 仍以规划为主，未体现当前已落地功能 |
| `static/js/app.js` | 文件头仍标注 v1.1，但功能已超过 v1.2 |
| `static/sw.js` | 缓存名为 `docblog-v1.3`，但没有对应正式 v1.3 文档 |
| `README.md` | 基础说明较完整，但 API 清单和功能清单滞后于代码 |

结论：v1.3 不应继续优先堆功能，而应先做服务治理和工程质量收敛。

## 2. 关键问题与风险

### 2.1 高优先级问题

| 优先级 | 问题 | 影响 | 涉及位置 |
|--------|------|------|----------|
| P0 | 静态文件服务未校验目录边界，存在 `../` 路径逃逸风险 | 可能读取 `static/` 外的文件，例如服务端源码或配置 | `server.py` `_serve_static()` |
| P0 | 修改数据的接口使用 GET，且无鉴权、无 CSRF 防护 | 任意网页或局域网请求可能触发删除、重建、改分类等操作 | `/api/delete`、`/api/purge`、`/api/reindex`、`/api/recategorize` 等 |
| P0 | 服务监听 `0.0.0.0` 且 JSON 响应 CORS 为 `*` | 如果在局域网可达，攻击面大于“本地个人工具”预期 | `main()`、`_json()` |
| P0 | Markdown 转 HTML 未统一转义正文和表格内容 | 文档内容可注入 HTML/脚本，存在 XSS 风险 | `md_to_html()`、`inline_html()` |
| P1 | 参数缺少统一校验，`page`、`limit`、`id` 直接转换或传入 | 异常请求可能中断处理；负数/超大 limit 会拖垮查询 | `do_GET()` 与各 API |
| P1 | 测试脚本直接修改真实数据 | `test_management.py` 会软删除/恢复，并批量改变真实文档分类且不还原 | `test_management.py` |

### 2.2 中优先级问题

| 优先级 | 问题 | 影响 |
|--------|------|------|
| P1 | 单线程 HTTPServer，重建索引或图谱会阻塞其它请求 | 搜索和页面访问会被长任务卡住 |
| P1 | 增量导入只判断 mtime，注释提到 size+mtime 但实现未使用 size | 文件替换、时间戳异常时可能漏更新 |
| P1 | 增量导入不处理已删除源文件 | 源 Markdown 删除后，数据库仍保留旧文档 |
| P2 | 前端已实现 `parseSearchQuery()`，但后端搜索仍只做基础清洗 | 高级搜索语法没有真正生效 |
| P2 | 健康检查中 `uptime` 实际是请求数，内存指标通常为空 | 运维指标语义不准确 |
| P2 | 前端错误和性能表在请求时动态建表 | 表结构迁移分散，不利于版本治理 |
| P2 | 日志无轮转、无结构化字段 | 长期运行后日志不可控，排障成本高 |
| P2 | API 错误统一返回不足，部分错误仍是 HTTP 200 + `{error}` | 前端难以区分业务错误和系统错误 |

## 3. v1.3 迭代目标

### 3.1 核心目标

1. 把服务端从“可用脚本”提升到“可长期本地运行的可靠服务”。
2. 修复会导致文件泄露、误删、跨站触发、XSS 的高风险问题。
3. 建立可重复、可隔离、可自动化的测试体系。
4. 收敛配置、日志、迁移和版本文档，减少后续迭代成本。

### 3.2 非目标

1. 不在 v1.3 强行引入大型框架；保持标准库优先。
2. 不做多用户权限系统的完整产品化，只做本地服务必要保护。
3. 不重写前端 UI，只补齐与服务端治理相关的调用方式和错误处理。

## 4. 分阶段迭代方案

### 阶段 0：安全止血与启动稳定

建议周期：0.5-1 天  
优先级：最高

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| 静态文件目录边界校验 | 对请求路径做 URL decode、规范化、`resolve()`，确认最终路径在 `static/` 内 | 访问 `/../server.py`、`/%2e%2e/server.py` 均返回 403 或 404 |
| 创建日志目录前置 | 在配置日志 `FileHandler` 前执行 `DATA_DIR.mkdir(parents=True, exist_ok=True)` | 删除 `data/` 后首次启动不报错 |
| 参数安全边界 | 增加 `parse_int()`，统一限制 `page >= 1`、`1 <= limit <= 100` | 传入非法 page/limit 返回规范 JSON 错误，不中断服务 |
| 服务监听地址可配置 | 新增 `host` 配置，默认 `127.0.0.1`，确需局域网共享时手动改 `0.0.0.0` | 默认启动仅本机可访问 |
| 限制 CORS | 默认不返回 `Access-Control-Allow-Origin: *`，或只允许同源 | 外部 Origin 不能直接操作 API |

### 阶段 1：API 语义与本地保护

建议周期：1-2 天  
优先级：高

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| 修改型接口改 POST | 删除、恢复、彻底删除、改分类、重建索引、同步、重建图谱改为 POST | GET 请求不会改变数据 |
| 增加本地管理 Token | `config.json` 支持 `admin_token`，前端管理操作带 `X-Admin-Token` | 未带 token 的管理请求返回 401 或 403 |
| 统一 API 响应 | 成功返回 `{status:"ok", data:...}`，失败返回 `{status:"error", code, message}` | 前端 API 封装能按状态统一提示 |
| 增加 OPTIONS 处理 | 对必要的 POST API 返回明确的 CORS/Method 信息 | 浏览器预检请求不报错 |
| API 路由表化 | 用字典维护 `(method, path) -> handler`，替代长链路 `if path ==` | 新增接口只需注册路由，不继续拉长 `do_GET()` |

建议优先调整的接口：

| 当前接口 | 建议接口 | 说明 |
|----------|----------|------|
| `GET /api/delete?id=1` | `POST /api/documents/1/delete` 或 `POST /api/delete` | 软删除 |
| `GET /api/restore?id=1` | `POST /api/documents/1/restore` 或 `POST /api/restore` | 恢复 |
| `GET /api/purge?id=1` | `POST /api/documents/1/purge` 或 `POST /api/purge` | 彻底删除 |
| `GET /api/recategorize?id=1&slug=java` | `POST /api/recategorize` | 单篇改分类 |
| `GET /api/batch-recategorize?...` | `POST /api/batch-recategorize` | 批量改分类 |
| `GET /api/reindex` | `POST /api/reindex` | 全量重建 |
| `GET /api/graph-rebuild` | `POST /api/graph-rebuild` | 重建图谱 |

### 阶段 2：Markdown 渲染与内容安全

建议周期：1-2 天  
优先级：高

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| 正文 HTML 转义 | 在 `inline_html()` 处理前先对原文做 HTML escape，再应用允许的 Markdown 规则 | 文档中 `<script>` 以文本展示，不执行 |
| 链接协议白名单 | `href/src` 仅允许 `http`、`https`、相对路径、锚点；拒绝 `javascript:` | 恶意链接不会进入 DOM |
| 表格单元格转义 | 表头和表格内容统一走安全的 inline 渲染 | 表格内 HTML 不执行 |
| 代码块语言名清洗 | `language-*` 只允许字母、数字、短横线、下划线 | 无法通过代码块语言注入属性 |
| 可选引入 Markdown 库 | 若允许第三方依赖，可评估 `markdown-it-py` + sanitizer；否则保留当前轻量解析器但补安全边界 | 渲染能力和安全边界可测试 |

### 阶段 3：数据一致性与索引可靠性

建议周期：1-2 天  
优先级：高

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| 删除源文件同步 | 增量导入后对比 `seen_files` 与数据库现有文件，软删除或物理删除缺失文件 | 删除 Markdown 后执行同步，页面不再展示旧文档 |
| 文件变更指纹 | 保存 `file_mtime`、`file_size`、可选 `content_hash`，组合判断变更 | 替换同 mtime 文件也能被识别 |
| 导入事务边界 | 单次导入使用事务，失败回滚，避免 FTS 与 documents 半更新 | 中途异常不会留下脏索引 |
| 清理孤儿数据 | 全量重建后清理无文档标签、无效关系 | 标签和图谱计数准确 |
| 迁移集中管理 | 将新增列、新增表、索引迁移集中到 `init_db()`，记录 `schema_version` | 新旧数据库升级可重复执行 |

### 阶段 4：搜索能力收敛

建议周期：2-3 天  
优先级：中

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| 后端支持高级搜索 | 与前端 `parseSearchQuery()` 对齐，支持短语、排除词、分类、标签 | `category:java "Spring Boot" NOT 面试` 可正确执行 |
| FTS snippet 高亮 | 使用 SQLite FTS5 `snippet()` 或 `highlight()` 生成摘要 | 搜索结果展示匹配上下文和高亮 |
| 短中文词兜底 | 1-2 字查询自动使用 LIKE 或专门策略 | 搜索“云”“算法”等短词有稳定结果 |
| 查询异常兜底 | FTS 语法错误返回可理解提示，自动降级 LIKE | 输入特殊符号不导致 500 |
| 搜索性能基线 | 记录 50/95/99 分位响应耗时，固定样本回归 | 优化前后能量化对比 |

### 阶段 5：并发、长任务与可观测

建议周期：1-2 天  
优先级：中

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| HTTP 服务并发化 | 本地模式可切换为 `ThreadingHTTPServer`，SQLite 每请求独立连接 | 大文件加载和搜索互不阻塞 |
| 长任务异步化 | reindex、graph-rebuild 变为后台任务，提供任务状态 API | 重建期间前端能看到进度，不阻塞普通浏览 |
| 日志轮转 | 使用 `RotatingFileHandler`，限制单文件大小和备份数 | 长期运行日志不会无限增长 |
| 健康检查修正 | `uptime` 改为启动时长；补充数据库大小、文档数、索引状态 | `/api/health` 指标语义准确 |
| 监控查询接口 | 增加前端错误、性能指标的查询 API 或管理页入口 | 已上报数据可被查看和清理 |

### 阶段 6：测试体系重建

建议周期：1-2 天  
优先级：高

| 任务 | 方案 | 验收标准 |
|------|------|----------|
| 引入隔离测试库 | 测试使用临时目录、临时 SQLite，不读写真实 `data/docs.db` | 测试重复运行不会改变用户数据 |
| 脚本改断言测试 | 将 `test_api.py`、`test_management.py` 改为 pytest 或 unittest | CI/本地运行可明确通过/失败 |
| 安全回归用例 | 覆盖路径逃逸、XSS、非法参数、未授权管理操作 | P0 问题不会回归 |
| 导入回归用例 | 覆盖新增、修改、删除源文件、全量重建 | 导入逻辑行为明确 |
| 前端冒烟测试 | 至少覆盖首页、搜索、文章页、回收站入口 | 主要用户路径可快速验证 |

## 5. 推荐落地顺序

| 顺序 | 迭代项 | 原因 |
|------|--------|------|
| 1 | 静态路径逃逸修复 | 文件读取风险最高，改动小、收益大 |
| 2 | GET 修改接口改 POST + 管理 Token | 防止误触发和跨站触发破坏数据 |
| 3 | Markdown 安全渲染 | 文档内容进入 DOM，必须先建立安全边界 |
| 4 | 参数校验与统一错误 | 为后续 API 改造打基础 |
| 5 | 测试隔离 | 避免优化过程中破坏真实文档数据 |
| 6 | 导入一致性 | 解决长期使用后的脏数据问题 |
| 7 | 搜索增强 | 在服务稳定后再提升功能体验 |
| 8 | 并发与长任务 | 文档量继续增长后收益更明显 |

## 7. 方案细化建议

### 7.1 静态文件安全方案

核心原则：任何静态资源请求最终只能落在 `BASE_DIR/static` 内。

建议处理流程：

1. 对 URL path 做 `urllib.parse.unquote()`。
2. 去掉开头 `/` 后拼接到 `static_root`。
3. 对结果执行 `resolve()`。
4. 使用 `relative_to(static_root.resolve())` 或等价方式判断目录边界。
5. 不在目录内时返回 403。

验收样例：

| 请求 | 期望 |
|------|------|
| `/index.html` | 200 |
| `/css/style.css` | 200 |
| `/../server.py` | 403/404 |
| `/%2e%2e/server.py` | 403/404 |
| `/static/../server.py` | 403/404 |

### 7.2 本地管理保护方案

该项目是本地工具，不一定需要完整登录系统，但需要避免误触发和跨站触发。

建议策略：

1. 默认绑定 `127.0.0.1`。
2. 管理操作使用 POST。
3. 配置 `admin_token`，前端通过请求头传递。
4. CORS 默认同源。
5. 对危险操作保留二次确认。

危险操作清单：

- 全量重建索引。
- 重建知识图谱。
- 软删除、恢复、彻底删除。
- 单篇/批量修改分类。
- 后续新增的导入、清空、迁移类操作。

### 7.3 测试改造方案

当前测试脚本更像“手动连通性检查”，不适合作为回归测试。建议拆分为三类：

| 测试类型 | 覆盖范围 | 运行方式 |
|----------|----------|----------|
| 单元测试 | 分类规则、Markdown 渲染、搜索查询解析、参数校验 | 直接调用函数 |
| 集成测试 | API 路由、SQLite 导入、FTS 搜索、回收站 | 临时目录 + 临时 DB + 测试服务 |
| 冒烟测试 | 首页、搜索、文章详情、管理操作入口 | 启动服务后 HTTP 请求或浏览器测试 |

测试数据建议放在 `web-app/tests/fixtures/`，不要扫描整个上级文档目录。

### 7.4 数据导入一致性方案

建议为 `documents` 增加或补齐以下字段：

| 字段 | 用途 |
|------|------|
| `file_mtime` | 快速判断文件是否变化 |
| `file_size` | 辅助判断同时间戳不同内容 |
| `content_hash` | 精确判断内容变化 |
| `source_exists` 或 `deleted_at` | 标记源文件缺失 |
| `indexed_at` | 记录索引更新时间 |

增量同步流程建议：

1. 扫描源目录，得到当前文件集合。
2. 对每个文件比较 mtime + size，必要时计算 hash。
3. 新增或变化文件进入导入队列。
4. 数据库中存在但本轮未扫描到的文件，移入回收站或标记源文件缺失。
5. 在事务中更新 `documents`、`docs_fts`、`doc_relations`。
6. 返回新增、更新、删除、跳过、失败计数。

## 8. 验收标准

v1.3 完成后，至少满足：

1. 删除 `web-app/data/` 后可以首次启动并自动创建必要目录和数据库。
2. 访问 `../` 路径不能读取 `static/` 之外的文件。
3. 未授权请求不能执行删除、重建、改分类等管理操作。
4. GET 请求不会改变数据状态。
5. 含 `<script>`、`javascript:` 链接的 Markdown 不会执行脚本。
6. 非法 `page`、`limit`、`id` 请求返回稳定 JSON 错误。
7. 测试运行前后，真实 `data/docs.db` 内容不变化。
8. README、技术文档、版本标识与实际能力一致。

## 9. 后续架构判断

短期继续使用标准库是合理的，因为项目定位是本地轻量知识库，当前瓶颈主要不是框架能力，而是安全边界和工程治理。

当出现以下需求时，再考虑迁移到 FastAPI 或 Flask：

1. 多用户、登录、权限、审计成为刚需。
2. 需要 OpenAPI 文档和更复杂的请求校验。
3. 后台任务、异步处理、插件系统显著增加。
4. 需要部署为长期在线的团队服务。
5. API 数量继续增长，手写路由维护成本明显上升。

迁移前建议先完成 v1.3 的接口语义、测试和数据一致性改造。这样即使未来换框架，也能以已有测试作为行为保护网。
