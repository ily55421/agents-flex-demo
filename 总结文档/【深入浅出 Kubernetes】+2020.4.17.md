### **《深入浅出 Kubernetes》内容分析与总结**

本书分为“理论篇”和“实践篇”两大部分，通过11个章节，由浅入深地讲解了Kubernetes（K8s）的核心原理和阿里云ACK产品线上的典型问题处理方法。

#### **理论篇 (第1-6章) - 核心原理解析**

这部分旨在夯实基础，用一个简单易懂的“冰箱模型”贯穿始终，解释了K8s集群最核心的几个概念。

*   **第1章：控制器原理**
    *   **核心思想**：将复杂的K8s控制器原理，类比为一个**简易冰箱的进化过程**。
    *   **关键概念**：**统一入口**、**控制器**、**控制器管理器**、**SharedInformer**、**ListWatcher**。
    *   **核心逻辑**：控制器是集群的“大脑”，它不断地通过ListWatcher机制观察资源的“期望状态”（如用户打开门）和“实际状态”（如灯的状态），并驱动实际状态向期望状态靠拢（自动开灯）。这个过程是声明式API和调谐循环的精髓。
    *   **K8s映射**：用户操作 → API Server；冰箱组件 → 集群资源（Pod等）；控制器 → K8s Controller；冰箱入口 → API Server；SharedInformer → 高效监听API Server变化的缓存机制。

*   **第2章：集群网络详解**
    *   **核心思想**：以Flannel方案为例，从网络搭建和通信两个角度，剖析阿里云K8s集群网络。
    *   **关键概念**：**三次IP划分**（集群CIDR → 节点podCIDR → Pod IP），**VPC路由表**，**cni0虚拟网桥**，**veth设备**，**Flanneld vs Flannel CNI**。
    *   **核心逻辑**：跨节点Pod通信是理解的重点。数据包从Pod发出，经cni0网桥、节点eth0，通过**VPC路由表**直接转发到目标节点，再进入目标Pod。整个过程没有隧道封包，性能高。
    *   **四种通信场景**：本地通信、同节点Pod通信、跨节点Pod通信、Pod与外部实体通信。

*   **第3章：集群伸缩原理**
    *   **核心思想**：讲解阿里云K8s集群如何利用云原生能力动态增减节点。
    *   **关键概念**：**手动/自动添加已有节点**、**集群扩容**、**Cluster Autoscaler (CA)**、**弹性伸缩 (ESS)**。
    *   **核心逻辑**：
        *   **增加节点**：核心是`attach_node.sh`脚本，通过Token认证，完成节点准备（安装配置K8s组件）并注册到Master。
        *   **自动伸缩**：CA组件监听Pod的调度状态。当Pod因资源不足处于Pending状态时，CA会触发ESS，ESS自动创建新ECS并通过userdata脚本将其加入集群。
        *   **关键点**：扩容依据是资源的**“预订单”**，而非使用率。

*   **第4章：认证与调度**
    *   **核心思想**：详解用户如何安全地接入集群，以及Pod如何被分配到最合适的节点。
    *   **关键概念**：**双向数字证书认证（mTLS）**、**KubeConfig文件**、**调度器**、**预选**与**优选**。
    *   **核心逻辑**：
        *   **认证**：客户端和API Server互相验证对方证书，证书由共同的CA签发，形成信任链。
        *   **调度**：分为“预选”（过滤不满足条件的节点）和“优选”（为剩余节点打分），最终综合得分最高的节点胜出。

*   **第5章：集群服务的三个要点和一种实现**
    *   **核心思想**：深入剖析Service的本质及其基于iptables的实现。
    *   **三个要点**：
        1.  **本质**：服务是**负载均衡/反向代理**。
        2.  **模式**：实现模式是**“边车模式”**，每个节点都部署一个反向代理，而非集中式LVS。
        3.  **实现者**：`kube-proxy`是一个**控制器**，监听Service和Endpoints变化并生成代理配置。
    *   **iptables实现**：将netfilter框架比作“固定切口”的管道过滤器。kube-proxy通过创建`KUBE-SERVICE`、`KUBE-SVC-XXX`、`KUBE-SEP-XXX`等自定义链，模块化地实现DNAT，将访问Service ClusterIP的流量随机转发到后端的Pod IP。

*   **第6章：镜像拉取这件小事**
    *   **核心思想**：剖析私有镜像自动拉取背后的OAuth 2.0协议和K8s实现机制。
    *   **关键概念**：**OAuth 2.0协议**、**docker login原理**、**imagePullSecrets**、**Service Account**、**准入控制**。
    *   **核心逻辑**：
        *   Docker拉取私有镜像的流程，本质是基于OAuth 2.0协议获取临时Token进行鉴权。
        *   K8s通过将认证信息（`dockerconfigjson`）存为`Secret`，并挂载到Pod上，实现了自动拉取。通过`Service Account`和准入控制器，可以进一步实现全局默认的私有镜像拉取能力。

#### **实践篇 (第7-11章) - 典型问题排障**

这部分记录了阿里云ACK产品线上遇到的真实疑难杂症及其排查过程，极具实战价值。

*   **第7章 & 第8章：集群节点NotReady问题排查（姊妹篇）**
    *   **章1：排查systemd和dbus**
        *   **问题现象**：节点低概率NotReady，`kubelet`正常，PLEG报告不健康，docker无响应。
        *   **排查路径**：docker daemon调用栈 → containerd调用栈 → runC调用栈 → **发现runC卡在与systemd的dbus通信上**。
        *   **根因**：systemd处理dbus消息时，用于追踪消息的`cookie`值（32位）因频繁创建/删除Unit而**溢出（>0xffffff）**，导致无法封装新消息，引发系统级阻塞。
    *   **章2：排查Terway网络插件**
        *   **问题现象**：节点NotReady，重启kubelet后仅就绪3分钟。
        *   **排查路径**：PLEG检查超时（3分钟）→ kubelet调用栈停在Pod网络配置 → **Terway插件堆积**，都在等待Terwayd守护进程 →Terwayd调用栈显示，一个核心线程使用netlink与内核通信时卡死。
        *   **根因**：Terwayd使用`netlink`库进行网络配置时，一个线程在内核的`recvfrom`系统调用上永久阻塞，导致所有网络操作排队等待。
        *   **修复**：为netlink操作增加超时机制，避免永久阻塞。

*   **第9章：我们为什么会删除不了集群的命名空间？**
    *   **问题现象**：命名空间状态一直是Terminating，无法删除。
    *   **排查路径**：kube-controller-manager日志显示清理资源的循环失败 → 失败在获取`metrics.k8s.io/v1beta1`这个API分组 → API Server也报同样错误 → 发现API Server访问Metrics Server Pod网络不通。
    *   **根因**：负责维护VPC路由表的`RouteController`，因其所在ECS的**RAM角色授权策略被错误修改为`Deny`**，无法访问VPC信息，导致到Metrics Server的路由规则缺失未被修复，APIServer与MetricsServer通信失败。
    *   **问题大图**：该问题串联了API Server、Metrics Server、Controller、VPC路由、RAM权限等多个组件，展现了问题的传导效应。

*   **第10章：阿里云ACK产品安全组配置管理**
    *   **核心思想**：系统性地讲解安全组在ACK集群中的角色、配置方法和常见问题。
    *   **关键点**：
        1.  **角色**：集群节点的"出入防火墙"。
        2.  **三种必配场景**：
            *   **限制集群访问外网**：必须放行Pod网段、阿里云内网地址段（100.64.0.0/10）及特定云服务公网地址。
            *   **IDC与集群互访**：双向放行对方网段。
            *   **多安全组管理**：可能导致管控面ENI（托管集群）或节点间通信失败，需相互授权。
        3.  **典型问题**：Pod跨节点通信失败（安全组规则被删）、kubectl exec/logs失败（管控ENI被隔离）。

*   **第11章 & 第12章：Istio服务网格问题排查**
    *   **章1：“二分之一活”的微服务**
        *   **问题现象**：所有Pod状态都显示`1/2`，即sidecar就绪。
        *   **排查路径**：istio-proxy的readiness probe失败 → pilot-agent报错Envoy未就绪 → envoy报错无法从Pilot获取配置 → **最终发现是kube-dns服务的ClusterIP被改，导致sidecar容器内无法解析Pilot服务名**。
    *   **章2：半夜两点CA证书过期**
        *   **问题现象**：节点重启后，无法创建新的虚拟服务和Pod，Citadel组件不断重启。
        *   **排查路径**：报错显示`Failed to create a self-signed Citadel` → 自签名证书验证失败。
        *   **根因**：**Istio自签名的CA根证书过期**（通常有效期为一年）。过期后，系统无法再签发新的工作负载证书，导致Citadel等核心功能失效。
        *   **解决**：删除过期的`istio-ca-secret`，重启Citadel使其重新生成。

# 《深入浅出 Kubernetes》核心内容汇总

> 本书由阿里云开发者社区出品，作者声东。通过理论讲解与实战排障相结合的方式，深入浅出地剖析了Kubernetes的核心原理与阿里云ACK产品的典型问题。

---

## 一、 理论篇：核心原理透析

### 1. 控制器原理：集群的大脑
- **形象比喻**：以“简易冰箱”的自动控制（开门亮灯、温控制冷）来解释控制器的工作模式。
- **核心机制**：通过**ListWatcher**监听资源状态，不断将“实际状态”调整为“期望状态”的**调谐循环**。
- **关键组件**：Controller、Controller Manager、SharedInformer。
- **要点**：控制器是K8s实现自动化、智能化的核心，它使集群摆脱了被动执行命令的角色。

### 2. 集群网络详解：Flannel方案
- **IP分配层级**：`集群CIDR` -> `节点podCIDR` -> `Pod IP`，实现三次网络划分。
- **跨节点通信**：不依赖隧道封装，直接通过**VPC路由表**转发，性能高效。
- **关键设备**：`cni0` (虚拟网桥)、`veth pair` (连接Pod和网桥)。
- **重要区分**：`flanneld` (DaemonSet，搭建网络干道) vs `flannel CNI` (二进制插件，为具体Pod创建网络)。

### 3. 集群伸缩原理：弹性扩缩容
- **节点增加**：
    - **核心脚本**：`attach_node.sh`，负责将裸ECS配置成K8s节点。
    - **自动伸缩**：**Cluster Autoscaler** 监听Pod状态，当Pod因资源不足(Pending)时，触发**ESS**创建新节点。
    - **扩缩依据**：基于资源的**“预订单”**，而非实际使用率。
- **节点减少**：根据节点加入方式（手动/自动/CA），通过清理userdata、从集群移除、执行`kubeadm reset`等组合操作完成。

### 4. 认证与调度：用户入口与Pod安排
- **认证**：
    - 采用**双向TLS数字证书认证（mTLS）**，保障客户端与API Server通信安全。
    - **KubeConfig**文件是认证的核心凭证，包含了客户端证书、密钥和集群CA证书。
- **调度**：
    - **预选阶段**：筛除不满足资源需求、端口冲突等硬性条件的节点。
    - **优选阶段**：对剩余节点按CPU/内存平衡性、亲和性等软性条件打分，**分高者胜出**。

### 5. 集群服务：要点与iptables实现
- **三个要点**：
    1.  **本质**：服务即**负载均衡/反向代理**。
    2.  **模式**：采用**边车（Sidecar）模式**，每个节点运行一个代理，而非集中的单点。
    3.  **控制**：`kube-proxy` 是一个典型的K8s控制器。
- **iptables实现**：
    - 在`PREROUTING`和`OUTPUT`链上执行**DNAT**（目标地址转换）。
    - 通过`KUBE-SERVICE` -> `KUBE-SVC-xxx` -> `KUBE-SEP-xxx` 的自定义链结构，实现从Service IP到具体Pod IP的负载均衡跳转。

### 6. 镜像拉取：私有镜像自动拉取
- **基础协议**：基于**OAuth 2.0**，以临时Token代替用户名密码进行鉴权。
- **K8s实现**：
    - **基础**：用户创建包含认证信息的`Secret`，并在Pod中通过`imagePullSecrets`引用。
    - **进阶**：通过`Service Account`和**准入控制器**，实现命名空间内Pod自动挂载拉取凭据。
    - **阿里云方案**：`Acr credential helper`控制器进一步自动化，从ACR服务自动获取临时凭据并创建Secret。

## 二、 实践篇：经典问题排障

### 7 & 8. 节点NotReady问题排查（姊妹篇）
- **案例一：systemd cookie溢出**
    - **现象**：节点低概率变为NotReady。
    - **根因**：systemd的dbus消息ID (`cookie`) 32位溢出，导致系统僵死。
    - **教训**：基础设施组件的潜在bug在容器高频操作下会被放大。
- **案例二：Terway网络插件阻塞**
    - **现象**：节点NotReady，重启kubelet后仅维持3分钟就绪状态（PLEG检查超时）。
    - **根因**：Terwayd守护进程在通过`netlink`与内核通信时，线程永久阻塞，导致所有Pod网络操作排队。
    - **教训**：为不可靠的系统调用设置超时至关重要。

### 9. 删除不掉命名空间之谜
- **现象**：Namespace一直处于`Terminating`状态。
- **根因**：VPC路由规则缺失导致API Server无法访问Metrics Server，而路由规则缺失未被修复的原因是**RAM角色授权策略**被错误修改。
- **教训**：K8s的稳定强依赖于底层云资源，是一个“牵一发而动全身”的故障传导系统。

### 10. 安全组配置管理
- **核心角色**：集群节点的虚拟防火墙。
- **配置三重点**：
    1.  **外网访问限制**：必须放行Pod网段、阿里云服务内网段(100.64.0.0/10)及关键云产品公网地址。
    2.  **IDC互访**：需双向配置放行规则。
    3.  **多安全组管理**：易导致“脑裂”或管控通道中断，需配置相互授权。
- **常见故障**：Pod跨节点通信失败、`kubectl exec/logs` 超时等。

### 11 & 12. Istio服务网格排障
- **案例一：“二分之一活”的微服务**
    - **现象**：所有Pod的sidecar容器未就绪。
    - **根因**：`kube-dns`服务地址变更，导致sidecar（envoy）无法解析Pilot服务名，获取不到动态配置。
- **案例二：半夜CA证书过期**
    - **现象**：集群CA（Citadel）不断重启，无法创建新资源。
    - **根因**：Istio自签名CA证书有效期只有一年，过期后验证失败。
    - **解决**：删除过期Secret，重启Citadel使其重生新证书。
