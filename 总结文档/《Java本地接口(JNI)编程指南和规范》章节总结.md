## 序言：关于本书
### 核心论点
- 本书旨在帮助开发者理解和使用 Java 本地接口（JNI），以便在 Java 应用程序中集成 C/C++ 代码，或实现 Java 虚拟机。
- JNI 是 Java 平台的一部分，确保了本地代码与不同 JVM 实现之间的互操作性和二进制兼容性。

### 关键概念/事件
- **目标读者**：需要整合传统 C/C++ 代码的 Java 开发者、JVM 实现者、对语言互操作性感兴趣的技术人员。
- **设计背景**：JNI 由 Sun Microsystems 工程师及社区共同设计，取代了 JDK 1.0 中存在的缺陷本地接口。
- **内容结构**：分为介绍与教程、编程指南、规范参考三部分。

### 逻辑推演/叙事脉络
序言介绍了书籍的受众、设计原理及贡献者。它强调了 JNI 的重要性在于允许利用现有本地代码库而不放弃 Java 平台优势，同时指出了 JNI 规范对于确保不同 JVM 实现间兼容性的关键作用。

### 经典金句/数据
> “JNI 的设计引来了在 Sun Microsystems 和 Java 技术授权之间的一些列争论... JNI 是来自 Netscape 的 JRI(Java Runtime Interface)的部分进化而来。”

## 第1章：介绍 (Introduction)
### 核心论点
- JNI 是 Java 平台与主机环境（Host Environment）之间的双向桥梁，允许 Java 代码调用本地代码，反之亦然。
- 使用 JNI 会牺牲 Java 的可移植性和类型安全性，因此应谨慎使用，仅在必要时（如性能关键、访问特定硬件/OS 特性）采用。

### 关键概念/事件
- **Java 平台 vs 主机环境**：Java 平台提供跨平台抽象，主机环境涉及具体 OS、CPU 和本地库。
- **JNI 的作用**：双向接口，支持本地库（Native Libraries）和本地应用（Native Applications）嵌入 JVM。
- **使用代价**：失去平台无关性（需重新编译本地代码）、失去类型安全（C/C++ 指针风险）。
- **替代方案**：RPC、JDBC、Java IDL 等进程间通信方式通常更安全，但 JNI 适用于同进程内高效交互。
- **演化历史**：从 JDK 1.0 的不稳定本地接口演进至 JDK 1.1 引入的 JNI，并在 Java 2 SDK 1.2 中标准化。

### 逻辑推演/叙事脉络
本章首先定义 Java 平台与主机环境的区别，引出 JNI 作为两者桥梁的角色。接着分析使用 JNI 的利弊（功能强大但牺牲安全与移植性），列举适用场景（如高性能计算、遗留库集成）。最后回顾 JNI 从 JDK 1.0 到 Java 2 的演化过程，强调其标准化和向后兼容性。

### 经典金句/数据
> “记住一旦一个应用程序使用了 JNI，它冒险失去了 Java 平台的两个好处：可移植性和类型安全。”

## 第2章：Hello World 示例 (Example Programs)
### 核心论点
- 通过一个简单的“Hello World”程序，演示编写和运行 JNI 程序的标准流程：声明 native 方法、编译 Java 类、生成头文件、实现 C 代码、编译本地库、运行程序。

### 关键概念/事件
- **开发步骤**：
    1. 编写 Java 类声明 `native` 方法。
    2. 使用 `javac` 编译 `.java` 文件。
    3. 使用 `javah -jni` 生成 C 头文件（`.h`）。
    4. 编写 C/C++ 实现文件（`.c`/.cpp），包含 `jni.h` 和生成的头文件。
    5. 编译生成本地库（`.dll` 或 `.so`）。
    6. 设置库路径并运行 Java 程序。
- **关键函数**：`System.loadLibrary()` 用于加载本地库；`JNIEXPORT` 和 `JNICALL` 宏确保导出和调用约定正确。
- **参数签名**：本地 C 函数接收 `JNIEnv*` 和 `jobject`（或 `jclass`）作为前两个参数。

### 逻辑推演/叙事脉络
本章通过分步指南展示了一个最小化的 JNI 示例。从 Java 端声明 native 方法开始，逐步过渡到工具链的使用（javac, javah），再到 C 语言的实现细节，最后解释如何链接和运行。每一步都解释了其目的和注意事项，如库命名规范和路径设置。

### 经典金句/数据
> “本地方法的声明必须包含 'native' 修饰字符... 本地方法声明是用分号终止的，因为在这类自身中本地方法没有实现。”

## 第3章：基本类型、字符串和数组 (Basic Types, Strings, and Arrays)
### 核心论点
- JNI 提供了特定的数据类型映射规则，用于在 Java 基本类型/引用类型与 C/C++ 类型之间转换。
- 字符串和数组不能直接作为 C 原生类型访问，必须通过 JNI 函数进行转换或复制，以管理内存和垃圾回收。

### 关键概念/事件
- **类型映射**：Java `int` -> `jint`, `boolean` -> `jboolean`, `String` -> `jstring`, `Object[]` -> `jobjectArray`。
- **字符串处理**：
    - `GetStringUTFChars` / `ReleaseStringUTFChars`：获取 UTF-8 格式的 C 字符串副本或指针。
    - `NewStringUTF`：从 C 字符串创建 Java String。
    - `GetStringCritical`：Java 2 SDK 1.2 新增，可能返回直接指针，但限制严格（禁止阻塞、GC 暂停）。
- **数组处理**：
    - `Get<Type>ArrayRegion` / `Set<Type>ArrayRegion`：复制数组元素到预分配缓冲区（推荐用于小数组或部分访问）。
    - `Get<Type>ArrayElements` / `Release<Type>ArrayElements`：获取指向数组元素的指针（可能是副本）。
    - `GetPrimitiveArrayCritical`：类似 String Critical，用于高性能访问，但有严格限制。
- **对象数组**：使用 `GetObjectArrayElement` 和 `SetObjectArrayElement` 逐个访问，不支持批量获取。

### 逻辑推演/叙事脉络
本章首先介绍基本类型的直接映射，然后深入讨论复杂的引用类型。对于字符串，对比了 UTF-8 和 Unicode 处理方式，强调了资源释放的重要性以防内存泄漏。对于数组，区分了基本类型数组和对象数组的不同访问策略，并引入了 Java 2 SDK 1.2 中的“Critical”系列函数以提升性能，同时警告其使用限制（避免死锁）。

### 经典金句/数据
> “不要忘记调用 ReleaseStringUTFChars... 没有调用 ReleaseStringUTFChars 将导致内存泄漏。”
> “在 Get/ReleaseStringCritical 对之间的本地代码，不应该出现阻塞调用或在 Java 虚拟器中分配新对象。否则，虚拟器可能锁死。”

## 第4章：成员域和方法 (Fields and Methods)
### 核心论点
- 本地代码可以通过 JNI 访问 Java 对象的实例域和静态域，以及调用实例方法和静态方法。
- 为了提高性能，应缓存 FieldID 和 MethodID，避免每次访问都进行昂贵的符号查找。

### 关键概念/事件
- **访问域**：
    - `GetFieldID` / `GetStaticFieldID`：获取域 ID，需指定类、域名和域描述符（如 `"I"` 表示 int, `"Ljava/lang/String;"` 表示 String）。
    - `Get/Set<Int/Object>Field`：读取或修改域值。
- **调用方法**：
    - `GetMethodID` / `GetStaticMethodID`：获取方法 ID，需指定方法名和描述符（如 `"()V"` 表示无参 void 方法）。
    - `Call<Void/Object/Int>Method`：执行方法调用。
    - `CallNonvirtualMethod`：调用超类方法或构造函数。
- **描述符**：使用 `javap -s` 工具查看正确的域和方法描述符。
- **缓存策略**：
    - **使用时缓存**：在 native 方法中使用静态变量缓存 ID，首次计算后复用。
    - **初始化时缓存**：在类的静态初始化块中调用 native 方法预计算 ID，更高效且线程安全。

### 逻辑推演/叙事脉络
本章先演示如何访问实例域和静态域，强调描述符的正确格式。接着介绍方法调用，包括实例方法、静态方法和构造函数。随后重点讨论性能优化，对比了两种缓存 FieldID/MethodID 的策略，推荐使用静态初始化块进行缓存以避免重复查找和线程竞争问题。最后分析了 JNI 调用的性能开销。

### 经典金句/数据
> “得到成员域和方法 ID 需要基于名字和成员域或方法的描述符的符号的查找。符号的查找是相对费时的。”
> “如果可行的话，最好是在它们定义类的静态初始化中来缓冲成员域和方法 IDs。”

## 第5章：局部和全局引用 (Local and Global References)
### 核心论点
- JNI 引用分为局部引用、全局引用和弱全局引用，它们具有不同的生命周期和垃圾回收行为。
- 正确管理引用对于防止内存泄漏、避免无效引用错误以及控制垃圾回收至关重要。

### 关键概念/事件
- **局部引用 (Local Reference)**：
    - 仅在创建它的 native 方法调用期间有效。
    - 方法返回后自动释放。
    - 不能跨线程使用。
    - 过多创建可能导致局部引用表溢出，需手动 `DeleteLocalRef` 或使用 `Push/PopLocalFrame`。
- **全局引用 (Global Reference)**：
    - 通过 `NewGlobalRef` 创建，需手动 `DeleteGlobalRef` 释放。
    - 跨线程、跨方法调用有效。
    - 阻止对象被垃圾回收。
- **弱全局引用 (Weak Global Reference)**：
    - Java 2 SDK 1.2 引入，通过 `NewWeakGlobalRef` 创建。
    - 不阻止垃圾回收，使用前需检查是否仍有效（`IsSameObject(obj, NULL)`）。
- **引用比较**：使用 `IsSameObject` 判断两个引用是否指向同一对象。

### 逻辑推演/叙事脉络
本章详细解释了三类引用的特性和使用场景。首先指出局部引用的局限性（生命周期短、不可跨线程），并通过错误示例说明缓存局部引用的危害。接着介绍全局引用作为解决方案，用于长期持有对象。最后引入弱全局引用，用于缓存类引用等场景，允许对象被 GC 回收。强调了资源释放的重要性及 `Push/PopLocalFrame` 的管理优势。

### 经典金句/数据
> “局部引用只在创建它们的线程中有效。一个在一个线程中创建的局部引用不能在另一线程中被使用。”
> “弱全局引用允许引用的对象被垃圾收集。”

## 第6章：异常 (Exceptions)
### 核心论点
- JNI 不会自动中断本地代码执行当异常发生时，开发者必须显式检查和处理异常。
- 忽略未决异常而继续调用 JNI 函数会导致未定义行为或 JVM 崩溃。

### 关键概念/事件
- **异常检测**：
    - `ExceptionOccurred`：返回异常对象引用。
    - `ExceptionCheck`：Java 2 SDK 1.2 引入，仅返回 boolean，更高效。
    - 检查返回值：许多 JNI 函数出错时返回 NULL 或错误码，并伴随异常抛出。
- **异常处理**：
    - **立即返回**：让异常传播到 Java 层处理。
    - **清除异常**：调用 `ExceptionClear` 后执行本地恢复逻辑。
    - **抛出异常**：使用 `ThrowNew` 或 `Throw` 创建新异常。
- **工具函数**：建议封装 `JNU_ThrowByName` 等工具函数简化异常抛出和局部引用清理。
- **安全调用列表**：在有未决异常时，只能调用少数几个 JNI 函数（如 `ExceptionClear`, `DeleteLocalRef`, `MonitorExit` 等）。

### 逻辑推演/叙事脉络
本章首先展示如何在 native 方法中捕获 Java 抛出的异常，并演示如何清除异常或抛出新的异常。强调了 JNI 异常模型与 C++/Java 不同，它是“粘性”的，不会自动跳转控制流。接着列出在异常状态下安全的 JNI 函数子集，警告违规调用的后果。最后提供了实用工具函数示例，展示如何规范化异常处理和资源清理。

### 经典金句/数据
> “通过 JNI 产生的一个未决的异常，不会立即中断本地方法的执行... JNI 编程者必须清晰地实现控制流程，在一个异常已经发生后。”
> “在调用任何后续的 JNI 函数前，检查，处理和清楚一个未决的异常是非常重要。”

## 第7章：调用接口 (Invocation Interface)
### 核心论点
- JNI 不仅允许 Java 调用本地代码，还允许本地应用通过“调用接口”嵌入 JVM。
- 这使 C/C++ 应用程序能够执行 Java 代码，实现双向集成。

### 关键概念/事件
- **创建 JVM**：使用 `JNI_CreateJavaVM` 初始化 JVM，获取 `JavaVM*` 和 `JNIEnv*`。
- **初始化参数**：
    - JDK 1.1：使用 `JDK1_1InitArgs`。
    - Java 2 SDK 1.2+：使用 `JavaVMInitArgs` 和 `JavaVMOption`，支持更多配置（如 classpath, heap size）。
- **附加线程**：非 Java 创建的本地线程需调用 `AttachCurrentThread` 获取 `JNIEnv*` 才能调用 JNI。
- **分离线程**：线程结束前调用 `DetachCurrentThread` 释放资源。
- **动态链接**：为避免依赖特定 JVM 库名，可使用 `dlopen`/`LoadLibrary` 动态加载 JVM 库并获取 `JNI_CreateJavaVM` 地址。

### 逻辑推演/叙事脉络
本章介绍如何将 JVM 嵌入到 C/C++ 应用中。首先展示基本的 `JNI_CreateJavaVM` 调用和参数配置。接着讨论多线程环境下，如何将本地线程附加到 JVM（Attach/Detach）。最后探讨了动态链接 JVM 库的方法，以提高应用程序对不同 JVM 实现的兼容性。

### 经典金句/数据
> “调用接口请求你来链接程序例如 invoke.c 和一个 Java 虚拟器实现。”
> “你需要一个方法来附加一个本地线程到一个正在运行的 Java 虚拟器上... 然后在不破坏其他附加线程情况下从虚拟器分离本地线程。”

## 第8章：JNI 的附加功能 (Additional JNI Features)
### 核心论点
- JNI 提供了线程同步、国际化支持、本地方法注册和库加载/卸载回调等高级功能。
- 正确处理线程模型匹配和字符编码转换对于构建健壮、国际化的本地应用至关重要。

### 关键概念/事件
- **线程同步**：
    - `MonitorEnter` / `MonitorExit`：对应 Java 的 `synchronized` 块。
    - `Wait` / `Notify`：通过调用 `Object.wait()` 等方法实现，无直接 JNI 函数。
    - **线程模型匹配**：本地代码使用的线程库必须与 JVM 使用的线程模型（如 Green Threads vs Native Threads）兼容，否则可能导致死锁。
- **国际化**：
    - Java String 内部为 Unicode，本地系统多为特定编码（如 GBK, UTF-8）。
    - 使用 `JNU_NewStringNative` 和 `JNU_GetStringNativeChars` 工具函数进行编码转换，避免直接使用 `GetStringUTFChars` 处理文件名等非 ASCII 内容。
- **注册本地方法**：`RegisterNatives` 允许显式绑定 Java 方法名到 C 函数指针，无需遵循严格的命名规范，支持动态更新实现。
- **加载/卸载回调**：
    - `JNI_OnLoad`：库加载时调用，可用于缓存 VM 指针、版本检查。
    - `JNI_OnUnload`：类加载器 GC 时调用，用于清理全局资源。

### 逻辑推演/叙事脉络
本章涵盖多个进阶主题。首先讨论多线程环境下的同步机制和线程模型兼容性警告。接着解决国际化问题，提供标准的编码转换模式。然后介绍 `RegisterNatives` 的灵活用法。最后详细说明 `JNI_OnLoad` 和 `JNI_OnUnload` 的生命周期及其在资源初始化和清理中的应用，特别是弱全局引用在卸载时的安全性。

### 经典金句/数据
> “如果 Java 虚拟器实现和本地代码有不同的线程和同步概念... 应用程序锁死。”
> “JNI_OnUnload 处理程序在最后运行... 应避免复杂的可能导致死锁的锁操作。”

## 第9章：利用存在的本地库 (Leveraging Existing Native Libraries)
### 核心论点
- 封装现有 C/C++ 库有两种主要策略：一对一映射（One-to-One Mapping）和共享存根（Shared Stubs）。
- Peer 类模式可用于将本地数据结构映射为 Java 对象，但需注意资源管理和一致性。

### 关键概念/事件
- **一对一映射**：为每个 C 函数编写一个对应的 JNI 包装函数。优点是类型安全、性能好；缺点是工作量大的。
- **共享存根**：创建一个通用的 JNI 函数（如 `CFunction.callInt`），通过反射或参数数组动态调用任意 C 函数。优点是开发快；缺点是性能低、类型不安全、易出错。
- **Peer 类**：Java 对象持有一个指向本地结构体的长整型指针（peer）。
    - **风险**：直接操作 peer 可能破坏 Java 对象状态的一致性。
    - **资源释放**：必须在 `finally` 块或 `finalize` 方法中释放本地资源，防止内存泄漏。
    - **反向指针**：本地结构体可持有 Java 对象的全局/弱全局引用，以实现回调。

### 逻辑推演/叙事脉络
本章探讨如何高效封装大量现有 C 库。首先对比了一一映射和共享存根的优劣，指出共享存根虽便捷但牺牲了类型安全。随后引入 Peer 类概念，展示如何在 Java 对象和本地结构体之间建立关联。重点讨论了 Peer 类的资源管理陷阱，强调显式释放和终结器的配合使用，以及如何处理本地到 Java 的回调。

### 经典金句/数据
> “共享存根的主要优点是程序员不需要写在本地代码中写大量的存根函数... 然而，共享存根必须小心使用... 这破坏了 Java 编程语言的类型安全。”

## 第10章：陷阱和缺陷 (Traps and Pitfalls)
### 核心论点
- JNI 编程中存在许多常见错误，如忽略错误检查、误用引用、线程安全问题等，需格外警惕。
- 遵循最佳实践可避免崩溃、内存泄漏和数据不一致。

### 关键概念/事件
- **错误检查缺失**：必须检查每个 JNI 调用的返回值和异常状态。
- **无效参数**：JNI 函数不检查参数有效性，传入 NULL 或错误指针会导致崩溃。
- **引用误用**：
    - 混淆 `jclass` 和 `jobject`。
    - 跨线程使用局部引用。
    - 缓存局部引用导致无效访问。
- **截断 jboolean**：`jboolean` 是 8 位，赋值时需确保只取低 8 位或使用三元运算符。
- **访问控制绕过**：JNI 可访问 private/final 字段，但修改 final 字段可能导致 JIT 优化失效或状态不一致。
- **国际化忽视**：直接使用 UTF-8 处理本地编码字符串会导致乱码。
- **资源泄漏**：忘记 `ReleaseStringChars`、`DeleteLocalRef` 等。
- **线程模型不匹配**：本地线程库与 JVM 线程模型冲突。

本章汇总了前十章中提到的常见错误和反模式。通过具体案例说明每种错误的后果（如崩溃、泄漏、逻辑错误）。涵盖了从基础的错误检查、类型转换，到高级的引用管理、线程安全和国际化问题。旨在作为开发者的自查清单。

## 第11章：JNI 设计概要 (Overview of the JNI Design)
### 核心论点
- JNI 的设计目标是实现二进制兼容性、效率和功能完整性。
- 通过抽象层（如 opaque references, function tables）隔离 JVM 内部实现，确保本地库可在不同 JVM 间移植。

### 关键概念/事件
- **设计目标**：
    1. **二进制兼容性**：同一本地库可在不同 JVM 实现上运行。
    2. **效率**：尽量减少开销，但在必要时牺牲效率以换取独立性。
    3. **功能完整**：提供足够的 API 操作 JVM。
- **类加载器与本地库**：本地库与加载它的 ClassLoader 绑定，防止命名空间冲突。
- **链接机制**：通过命名约定（`Java_Class_Method`）或 `RegisterNatives` 链接方法。
- **JNIEnv 指针**：线程局部存储，包含函数表指针，确保线程安全和解耦。
- **引用实现**：局部引用通过注册表实现，全局引用直接指向堆对象。
- **数组访问妥协**：提供 Copy 和 Pin 两种模式，平衡性能与 GC 复杂度。

### 逻辑推演/叙事脉络
本章从架构角度解释 JNI 的设计决策。首先阐述三大设计目标。接着深入探讨类加载器如何隔离本地库，方法链接的命名规则，以及 JNIEnv 的线程局部特性及其优势。最后解释了引用和数组访问的内部实现机制，说明了为何采用当前的折衷方案（如 Copy/Pin）以兼顾 GC 效率和编程便利性。

### 经典金句/数据
> “JNI 设计的最重要目标是确保它在一个给定的主机环境上不同的 Java 虚拟器实现中提供二进制兼容性。”
> “JNIEnv 接口指针是一个线程局部数据的指针... 本地代码不该在另一个线程中使用属于这个线程的 JNIEnv 接口指针。”

## 第12章：JNI 类型 (JNI Types)
### 核心论点
- 本章定义了 JNI 使用的所有标准数据类型、描述符格式和常量，是开发的参考规范。

### 关键概念/事件
- **基本类型映射**：`jint` (32-bit), `jlong` (64-bit), `jboolean` (8-bit unsigned) 等。
- **引用类型层次**：`jobject` 为基类，`jclass`, `jstring`, `jarray` 等为子类。C++ 中有继承关系，C 中均为 typedef。
- **jvalue 联合体**：用于传递可变参数。
- **Field/Method IDs**： opaque 指针类型。
- **字符串格式**：
    - **Modified UTF-8**：JNI 使用变体 UTF-8，NULL 字符编码为两字节，不支持四字节序列。
- **描述符**：
    - **类**：`Ljava/lang/String;`
    - **数组**：`[I` (int[]), `[Ljava/lang/Object;` (Object[])
    - **方法**：`(参数类型)返回类型`，如 `(ILjava/lang/String;)Z`。
- **常量**：`JNI_TRUE/FALSE`, `JNI_OK/ERR`, `JNI_COMMIT/ABORT`, 版本号 `JNI_VERSION_1_1/1_2`。

### 逻辑推演/叙事脉络
本章作为规范参考，详细列出了所有 JNI 类型的定义、大小和用途。解释了 Modified UTF-8 的编码细节及其与标准 UTF-8 的区别。提供了完整的域和方法描述符语法规则。最后列出了常用的宏和常量定义，供开发者查阅。
