## 第1部分：Dubbo3.0 的演进及多语言解决方案的实践
**演讲人：** 曹胜利

### 核心论点
本章主要解决 Dubbo 在云原生时代面临的协议封闭、多语言支持弱以及与 Kubernetes/Service Mesh 体系割裂的问题。核心观点是 Dubbo 3.0 通过引入应用级服务发现、新一代 RPC 协议（基于 HTTP/2/Protobuf）以及对 Service Mesh 的深度支持，实现从 SDK 模式向云原生基础设施的演进，并促进与 Spring Cloud/gRPC 的互通。

### 关键概念/事件
- **应用级服务发现**：区别于 Dubbo 2.x 的接口级服务发现，3.0 改为以应用（App）为单位注册和订阅，大幅减少注册中心压力和数据推送量，提升性能。
- **新一代 RPC 协议**：基于 HTTP/2 和 Protobuf，支持 Reactive Stream（Request-Stream, Bi-Stream），内置流控（反压），区分 Metadata 与 Payload，更好地支持 Mesh 架构。
- **云原生支持**：Dubbo 融入 Kubernetes 生命周期，支持 K8s Native Service 发现（DNS/API-Server），支持 xDS 协议，实现 Thin SDK 以适配 Mesh。
- **Dapr 对比**：Dapr 作为 Multiple Runtime 实践者，提供标准 API（服务调用、状态管理、Pub/Sub等），屏蔽底层基础设施差异，与 Dubbo 3.0 在多语言和云原生方向上有互补和竞争关系。

### 逻辑推演/叙事脉络
演讲首先回顾 Dubbo 历史，指出 2.x 版本在云原生时代的局限性。接着引出 Dubbo 3.0 的三大背景：新一代 RPC 协议需求、应用级服务发现优化、云原生支持。详细阐述了应用级服务发现如何通过 MD5 合并机制优化性能，以及新协议如何支持 Mesh 和多语言。最后介绍 Dubbo-go 内部版本实践及 Dapr 的概念，展示阿里在多语言微服务生态上的布局。

### 经典金句/数据
> “Dubbo 3.0 的方向：应用级服务发现、云原生支持、新一代 RPC 协议。”
> “Mesh 带来的挑战：xDS 有成为标准的可能，原有的 SDK 逻辑和 mesh 逻辑重复。”

## 第2部分：托管式服务网格：多种类型计算服务统一管理的基础设施
**演讲人：** 王夕宁

### 核心论点
本章旨在解决混合部署环境下（K8s Pod、ECS VM、裸机）服务治理不统一的问题。核心观点是通过阿里云托管式服务网格（ASM），将服务通信能力抽象为基础设施，利用 Sidecar 模式实现业务代码零侵入，并提供统一的流量管理、安全认证和可观测性，支持非 K8s 工作负载纳入网格统一管理。

### 关键概念/事件
- **托管式服务网格（ASM）**：基于 Istio 兼容的托管控制平面，支持 ACK/ASK 集群及外部集群，降低运维复杂度。
- **混合部署支持**：通过 `WorkloadEntry` 和 `ServiceEntry`，将 ECS 虚拟机等非容器化应用纳入 Service Mesh 管理，实现统一的服务发现和治理。
- **本地优先负载均衡**：基于位置的路由能力，将流量路由到最靠近的容器或同一可用区，降低延迟和跨域流量费用。
- **统一安全与可观测性**：提供渐进式 mTLS、细粒度 RBAC 授权、OPA 策略管理；集成日志、链路追踪（Zipkin/SLS）和监控（Prometheus/Grafana）。
- **WASM 扩展**：支持基于 WebAssembly 的代理扩展插件动态加载和热更新，增强 Proxy 的可扩展性。

### 逻辑推演/叙事脉络
演讲从架构模式变迁（Lib -> Sidecar）切入，介绍 ASM 的产品架构及其对混合部署的支持。重点讲解了流量管理中的本地优先负载均衡策略，以及如何将非 K8s 负载（如 ECS）网格化。随后阐述了统一的安全体系（mTLS/RBAC）和可观测性方案（日志/追踪/监控）。最后介绍了基于 WASM 的扩展能力和服务网格成熟度模型。

### 经典金句/数据
> “Dev/Ops/SRE 团队将以统一的、声明的方式解决应用服务管理问题。”
> “相比于 Kubernetes 默认提供的轮询方式进行负载均衡，服务网格技术提供的基于位置的路由能力，可以将流量路由到最靠近的容器。”

## 第3部分：Service Mesh 在超大规模场景下的落地挑战
**演讲人：** 李云（至简）

### 核心论点
本章聚焦于阿里巴巴在超大规模微服务架构下落地 Service Mesh 面临的性能、稳定性和演进挑战。核心观点是通过“飞行中换引擎”策略，实现业务无感知的 Mesh 化演进，并通过优化 Istio/Envoy 内核（如内存优化、协议支持）及引入应用级服务发现，系统性解决大规模场景下的资源开销和稳定性问题。

### 关键概念/事件
- **超大规模挑战**：阿里电商生态庞大，Dubbo RPC 为主，Java 栈治理完备但其他语言偏弱；面临 Sidecar 规模化运维、历史包袱（如 Groovy 脚本耦合）等问题。
- **飞行中换引擎**：指在业务运行过程中平滑演进技术架构，短期价值在于中间件能力下沉、资源消耗可量化；长远价值在于业务与基础技术解耦。
- **流量无损透明拦截**：通过动态流量拦截实现无侵入业务 Mesh 化，支持流量无损热升级（Consumer/Provider 视角）。
- **系统性优化**：阿里向 Istio/Envoy 社区贡献 PR，解决性能 Bug，内存开销下降 50%；支持 Dubbo/RocketMQ 协议；探索 LEDS 协议以支持超大规模。
- **Sidecar 规模化运维**：基于 OpenKruise 的 SidecarSet 进行部署、灰度和升级，结合 OneOps 运维体系和阿里云监控产品。

### 逻辑推演/叙事脉络
演讲首先描述阿里分布式应用现状及 Mesh 落地挑战。接着提出“飞行中换引擎”的演进理念，强调短期与长远价值。详细技术方案包括流量无损拦截和热升级机制。随后深入探讨如何系统性解决超大规模问题，包括对开源社区的贡献和优化效果（CPU/内存下降）。最后介绍 Sidecar 的规模化运维方案。

### 经典金句/数据
> “‘不变’从来都无法消除‘技术债’的风险，‘还债’是常态。”
> “应用 mesh 化后数据推送的 CPU 开销大幅下降，内存开销下降。”
> “Envoy 开源社区：提交 14 个 PR，内存开销下降 50%，新增对 Dubbo、RocketMQ 协议的支持。”

## 第4部分：Spring Cloud Alibaba 在 Kubernetes 下的微服务治理最佳实践
**演讲人：** 方剑

### 核心论点
本章探讨 Spring Cloud Alibaba 在云原生（Kubernetes）环境下的演进与治理实践。核心观点是通过 Java Agent 和 Service Mesh 双模引擎，实现服务治理能力的下沉与透明化，解决 K8s 下 IP 不确定、SDK 升级成本高等问题，提供无损下线、离群实例摘除、全链路灰度等高级治理能力，并实现多语言互通。

### 关键概念/事件
- **云原生挑战**：K8s 下应用 IP 不确定导致治理规则失效；SDK 强依赖导致升级成本高；迁移上云成本高。
- **治理演进路线**：从 Fat-SDK/Pandora 到 One Agent/One Mesh，实现无侵入、0 升级成本、全面兼容开源。
- **Java Agent 治理**：通过字节码增强，无需修改代码即可享受微服务治理能力，如无损下线（PreStop + 主动通知）、离群实例摘除（实时性高、灵活策略）。
- **高级治理特性**：服务鉴权（白名单/黑名单、签名校验）、标签路由（基于 AZ/版本/自定义标）、金丝雀发布（按流量百分比或请求特征路由）、全链路灰度。
- **多语言互通**：通过 MCP/xDS 协议，实现 Java 微服务体系与 Service Mesh（Node.js/Go 等）在调用、监控、治理上的互通。

### 逻辑推演/叙事脉络
演讲回顾 Spring Cloud Alibaba 发展历史及现状，指出云原生下的挑战。提出后端服务 BaaS 化、治理下沉、多云混部等趋势。重点介绍基于 Java Agent 的无侵入治理方案，详细阐述无损下线、离群实例摘除、服务鉴权、标签路由和金丝雀发布的实现原理。最后展示 Java 体系与 Service Mesh 的多语言互通架构。

### 经典金句/数据
> “Java Agent 无需修改代码，享受微服务治理能力。”
> “标签是云原生环境下的一等公民。”
> “故障应急 1-5-10 原则：1 分钟发现，5 分钟定位，10 分钟恢复。”

## 第5部分：Nacos 内核构建及演进方向
**演讲人：** 李艳林

### 核心论点
本章针对 Nacos 1.x 在大规模使用下暴露的架构、质量和协作问题，提出 Nacos 2.x 的内核重构计划。核心观点是通过统一内核、采用 gRPC 长连接、优化存储与一致性协议，实现高性能、高可用和企业级标准，支撑百万级实例和百万级开发者生态。

### 关键概念/事件
- **Nacos 1.x 问题**：架构分层抽象不够、重复代码多、功能膨胀导致回归难、协作效率低（PR 冲突、文档缺失）。
- **Nacos 2.x 架构**：统一内核，采用 gRPC 长连接通道替代 HTTP 短连接，实现实例维度服务状态同步，提升实时性和性能。
- **高可用架构**：支持多级容灾（同城双活、异地多活），通过 NameServer 和 ADNS 实现域名访问和流量调度，Store 复制保证数据一致性。
- **企业级质量标准**：建立 SLA/Metrics/Tracing 可观测体系，强弱依赖管理，故障演练与预案机制，代码校验与压测流程。
- **三年小目标**：影响 100W+ 开发者，5W Star，100W 实例支持，99.99% 高可用，毫秒级推送。

### 逻辑推演/叙事脉络
演讲首先介绍 Nacos 定位及 1.x 版本的成果与生态地位。接着深入剖析 1.x 在架构、质量、协作方面的问题。随后重点阐述 2.x 的规划，包括架构重构（gRPC、统一内核）、高性能与高可用设计（多级容灾、同城/异地多活）。最后强调企业级质量保障体系及未来三年的发展目标。

### 经典金句/数据
> “Nacos 2.x 规划：统一内核、企业级标准、文档化协作。”
> “打造文档化协作模式（开放透明、多人协作、方便搜索），提升整体协作效率！”
> “目标：99.99% 高可用，毫秒级推送，100w 实例支持。”
