## 第一章：微服务介绍

### 核心论点
本章主要解决“为什么需要微服务架构以及Spring Cloud Alibaba在其中扮演什么角色”的问题。核心观点是：随着系统规模扩大，架构从单体向微服务演进是必然趋势，而Spring Cloud Alibaba提供了一站式分布式应用开发解决方案，有效降低了微服务落地的技术门槛。

### 关键概念/事件
-   **架构演变**：经历了单体应用→垂直应用→分布式架构→SOA→微服务架构的演进过程，每个阶段都是为了解决前一阶段的瓶颈（如耦合度高、扩展性差）。
-   **微服务核心问题**：服务治理（注册发现）、服务调用（REST/RPC）、服务网关、服务容错、链路追踪是微服务落地必须解决的五大基础设施问题。
-   **Spring Cloud Alibaba**：致力于提供微服务开发的一站式解决方案，包含Sentinel、Nacos、RocketMQ、Seata等核心组件，通过注解和少量配置即可接入阿里中间件生态。

### 逻辑推演/叙事脉络
作者首先回顾了互联网系统架构的五个发展阶段，分析了每种架构的优缺点及适用场景，引出微服务架构的必要性。接着指出微服务虽然带来了独立部署、原子化拆分等优势，但也引入了分布式系统的复杂性。最后顺势介绍Spring Cloud及其Alibaba版本，强调其作为“工具包”和“一站式方案”如何屏蔽底层复杂性，让开发者专注于业务。

### 经典金句/数据
> “微服务架构在某种程度上是面向服务的架构SOA继续发展的下一步，它更加强调服务的‘彻底拆分’。”
> “Spring Cloud并没有重复制造轮子，它只是将目前各家公司开发的比较成熟、经得起实际考验的服务框架组合起来……最终给开发者留出了一套简单易懂、易部署和易维护的分布式系统开发工具包。”

## 第二章：微服务环境搭建

### 核心论点
本章旨在解决“如何构建一个可运行的微服务电商案例环境”的问题。核心观点是：通过Maven父工程统一管理依赖版本，划分公共模块与业务微服务（用户、商品、订单），是实现微服务工程化落地的第一步。

### 关键概念/事件
-   **模块设计**：采用`springcloud-alibaba`父工程 + `shop-common`公共模块 + 三个业务微服务（user/product/order）的结构，端口规划清晰（807x/808x/809x）。
-   **服务调用雏形**：演示了最原始的微服务调用方式，即订单服务通过`RestTemplate`硬编码URL调用商品服务，暴露了地址写死、无负载均衡等问题。
-   **技术选型**：基于Spring Boot 2.1.3 + Spring Cloud Greenwich + Spring Cloud Alibaba 2.1.0，使用JPA作为持久层，MySQL 5.7作为数据库。

### 逻辑推演/叙事脉络
从技术选型出发，定义了项目的整体模块结构。随后按步骤创建父工程、公共模块及三个业务微服务，编写实体类、DAO、Service和Controller。重点演示了订单服务调用商品服务的代码实现，并通过浏览器访问验证了基本功能的连通性，为后续引入注册中心和负载均衡做铺垫。

### 经典金句/数据
> “我们一般把服务的主动调用方称为服务消费者，把服务的被调用方称为服务提供者。”
> -   版本对应表：Spring Cloud Greenwich 对应 Spring Cloud Alibaba 2.1.x.RELEASE 对应 Spring Boot 2.1.x.RELEASE。

## 第三章：Nacos Discovery-服务治理

### 核心论点
本章解决“如何实现微服务的动态注册发现与负载均衡”的问题。核心观点是：Nacos作为注册中心消除了硬编码地址，结合Ribbon或Feign可实现客户端负载均衡与服务调用的声明式简化。

### 关键概念/事件
-   **服务治理三要素**：服务注册（实例上报信息）、服务发现（获取实例清单）、服务剔除（心跳监测与健康检查）。
-   **Nacos实战**：作为Eureka+Config的结合体，支持服务注册发现与配置管理；通过`@EnableDiscoveryClient`注解接入。
-   **负载均衡策略**：Ribbon提供轮询、随机、加权响应时间等多种策略；Feign作为声明式HTTP客户端，默认集成Ribbon，使远程调用像本地方法一样简单。

### 逻辑推演/叙事脉络
先分析硬编码调用的弊端，引出服务治理概念。对比Zookeeper、Eureka、Consul后选择Nacos。实操环节依次将商品、订单服务注册到Nacos，演示自定义负载均衡与Ribbon负载均衡的区别。最后引入Feign替代RestTemplate，展示了从“手动拼接URL”到“接口注解调用”的开发体验升级。

### 经典金句/数据
> “Nacos是一个更易于构建云原生应用的动态服务发现、配置管理和服务管理平台。”
> “Feign是Spring Cloud提供的一个声明式的伪Http客户端，它使得调用远程服务就像调用本地服务一样简单。”

## 第四章：Sentinel-服务容错

### 核心论点
本章解决“高并发下如何防止服务雪崩并保障系统稳定性”的问题。核心观点是：Sentinel以流量为切入点，通过限流、熔断降级、系统负载保护等多维度规则，实现对服务稳定性的全方位防护。

### 关键概念/事件
-   **服务雪崩**：因下游服务不可用导致上游线程阻塞堆积，进而引发整个调用链瘫痪的级联故障。
-   **容错手段**：隔离（线程池/信号量）、超时、限流（QPS/线程数）、熔断（关闭/开启/半开状态）、降级（Fallback托底）。
-   **Sentinel规则体系**：包括流控规则（直接/关联/链路模式）、降级规则（RT/异常比例/异常数）、热点参数规则、授权规则及系统自适应保护规则。
-   **规则持久化**：默认规则存内存不稳定，需通过SPI扩展机制将规则持久化到文件或Nacos等数据源。

### 逻辑推演/叙事脉络
通过JMeter压测模拟Tomcat线程耗尽场景，直观展示雪崩效应。对比Hystrix、Resilience4j后引出Sentinel。详细讲解控制台安装与各类规则配置，特别是链路流控中`WEB_CONTEXT_UNIFY`参数的坑点。最后深入`@SentinelResource`注解用法及Feign整合Sentinel的FallbackFactory机制，完成从理论到实战的闭环。

### 经典金句/数据
> “我们无法完全杜绝雪崩源头的发生，只有做好足够的容错，保证在一个服务发生问题，不会影响到其它服务的正常运行。也就是‘雪落而不雪崩’。”
> -   Sentinel vs Hystrix：Sentinel采用信号量隔离+滑动窗口统计，支持实时控制台与动态规则推送；Hystrix采用线程池隔离，不支持控制台。

## 第五章：Gateway-服务网关

### 核心论点
本章解决“如何统一微服务入口并处理横切面关注点”的问题。核心观点是：Spring Cloud Gateway基于WebFlux构建，通过路由、断言、过滤器三大核心抽象，实现了高性能的动态路由转发与请求增强。

### 关键概念/事件
-   **核心架构**：Route（路由）、Predicate（断言/匹配条件）、Filter（过滤器/请求响应修改）是网关的三大基石。
-   **内置功能**：提供After/Before/Path/Header/Cookie等十余种断言工厂，以及StripPrefix/AddRequestHeader/Retry等过滤器工厂。
-   **自定义扩展**：支持继承`AbstractRoutePredicateFactory`或实现`GlobalFilter`接口来定制业务逻辑（如鉴权、日志）。
-   **网关限流**：集成Sentinel Adapter，支持基于Route ID或自定义API分组进行细粒度限流。

### 逻辑推演/叙事脉络
从客户端直连微服务的痛点出发，对比Nginx+Lua、Kong、Zuul等方案，确立Gateway的技术优势。由浅入深演示基础路由、Nacos动态发现、简写版配置。详解执行流程（Pre Filter → Proxy → Post Filter），并通过自定义Age断言和Auth全局过滤器展示扩展能力。最后整合Sentinel实现网关级限流。

### 经典金句/数据
> “Spring Cloud Gateway是Spring公司为了替换Zuul而开发的网关服务……性能强劲：是第一代网关Zuul的1.6倍。”
> “PRE过滤器在请求被路由之前调用……POST过滤器在路由到微服务以后执行。”

## 第六章：Sleuth-链路追踪

### 核心论点
本章解决“分布式环境下如何追踪请求链路与定位性能瓶颈”的问题。核心观点是：Sleuth通过TraceId和SpanId串联跨服务调用，结合Zipkin实现可视化监控，是微服务可观测性的关键基础设施。

### 关键概念/事件
-   **核心术语**：Trace（调用链树）、Span（工作单元）、Annotation（CS/SR/SS/CR时间节点）。
-   **Zipkin架构**：由Collector（收集）、Storage（存储）、RESTful API、Web UI四部分组成。
-   **数据持久化**：生产环境不建议使用内存存储，应配置MySQL或Elasticsearch作为后端存储。
-   **采样率**：通过`sleuth.sampler.probability`控制上报比例，1.0表示全量采集。

### 逻辑推演/叙事脉络
阐述分布式追踪的必要性，对比CAT、Pinpoint、SkyWalking等方案。介绍Sleuth原理及日志输出格式。实操集成Zipkin Server与Client，演示UI界面查询调用链耗时。针对生产需求，分别给出MySQL建表脚本与ES启动命令来实现追踪数据的持久化存储。

### 经典金句/数据
> “分布式链路追踪就是将一次分布式请求还原成调用链路，进行日志记录，性能监控并将一次分布式请求的调用情况集中展示。”
> -   Zipkin核心组件：Collector、Storage、RESTful API、Web UI。

## 第七章：Rocketmq-消息驱动

### 核心论点
本章解决“微服务间如何实现异步解耦与流量削峰”的问题。核心观点是：RocketMQ作为高性能消息中间件，通过普通、顺序、事务三种消息类型，支撑了从简单通知到分布式事务一致性的多种业务场景。

### 关键概念/事件
-   **MQ核心价值**：异步解耦（注册后发短信）、流量削峰（秒杀缓冲）。
-   **四大角色**：NameServer（协调者）、Broker（存储投递）、Producer（生产者）、Consumer（消费者）。
-   **消息类型**：同步/异步/单向发送；顺序消息（SyncSendOrderly）；事务消息（半事务+回查机制）。
-   **消费模式**：集群消费（一条消息只被一个实例消费）vs 广播消费（每个实例都消费）。

### 逻辑推演/叙事脉络
先讲MQ应用场景与产品选型，再搭建RocketMQ环境与控制台。通过订单下单发短信的案例，演示Spring Boot Starter的集成与消息收发。深入讲解三种发送方式的TPS与可靠性差异，重点剖析事务消息的“半事务-回查”交互流程，最后补充消费模式的配置细节。

### 经典金句/数据
> “半事务消息：暂不能投递的消息……服务端未收到生产者对该消息的二次确认，此时该消息被标记成‘暂不能投递’状态。”
> -   发送方式对比：同步发送（可靠、有反馈）、异步发送（快、回调处理）、单向发送（最快、无反馈）。

## 第八章：SMS--短信服务

### 核心论点
本章解决“如何在微服务中集成第三方云通信能力”的问题。核心观点是：通过阿里云SMS SDK封装工具类，并结合RocketMQ监听器，可实现业务触发与短信发送的解耦与自动化。

### 关键概念/事件
-   **接入流程**：实名认证→开通服务→获取AccessKey→申请签名/模板→调用API。
-   **核心API**：`SendSms`（发送短信）、`QuerySendDetails`（查询发送记录）。
-   **业务整合**：在`shop-user`服务中监听`order-topic`消息，解析订单信息后调用SmsUtil发送验证码。

### 逻辑推演/叙事脉络
简述短信服务产品优势。按步骤演示阿里云控制台配置与SDK调用Demo。将短信发送封装为静态工具类，并在RocketMQ消费者`SmsService`中注入UserDao获取手机号，实现“下单成功→MQ通知→自动发短信”的完整业务闭环。

### 经典金句/数据
> “短信服务(Short Message Service)是阿里云为用户提供的一种通信服务的能力……完美支撑双11期间20亿短信发送，6亿用户触达。”
> -   SendSms返回Code为"OK"代表请求成功。

## 第九章：Nacos Config--服务配置

### 核心论点
本章解决“微服务配置分散、无法动态刷新与环境隔离”的问题。核心观点是：Nacos Config通过集中化管理、Bootstrap优先级加载与`@RefreshScope`注解，实现了配置的实时热更新与多环境共享。

### 关键概念/事件
-   **配置中心痛点**：配置分散、环境区分难、修改需重启。
-   **加载优先级**：bootstrap.yml > application.yml；DataID命名规范需与配置文件严格对应。
-   **动态刷新**：使用`@RefreshScope`注解标注Bean，配合Nacos监听机制实现配置变更即时生效。
-   **配置共享**：支持同服务多环境共享（提取公共DataID）与跨服务共享（shared-dataids）。

### 逻辑推演/叙事脉络
分析传统配置管理缺陷，对比Apollo、Disconf、Spring Cloud Config。演示Nacos Config入门：创建bootstrap.yml、添加DataID、注释本地配置。深入讲解硬编码与注解两种动态刷新方式，以及通过命名空间、Group、DataID实现环境隔离与配置复用的最佳实践。

### 经典金句/数据
> “当配置中心中的各种参数有更新的时候，也能通知到各个服务实时的过来同步最新的信息，使之动态更新。”
> -   配置文件优先级：bootstrap.properties > bootstrap.yml > application.properties > application.yml。

## 第十章：Seata-分布式事务

### 核心论点
本章解决“微服务架构下如何保证跨库操作的数据一致性”的问题。核心观点是：Seata通过AT模式（两阶段提交优化）实现对业务无侵入的分布式事务控制，在保证最终一致性的同时大幅提升了性能。

### 关键概念/事件
-   **分布式事务模型**：DTP（AP/TM/RM）、可靠消息服务、最大努力通知、TCC（Try-Confirm-Cancel）。
-   **Seata三组件**：TC（事务协调器）、TM（事务管理器）、RM（资源管理器）。
-   **AT模式原理**：一阶段提交本地事务并记录undo_log，二阶段根据决议异步删除日志或反向补偿回滚，避免了长时间持锁。
-   **全局事务标识**：XID贯穿整个调用链，BranchID关联分支事务。

### 逻辑推演/叙事脉络
从本地事务ACID引申出分布式事务场景与挑战。对比XA、TCC、消息队列等方案优劣。介绍Seata设计理念与执行流程。实操环节包括：初始化undo_log表、配置DataSourceProxy代理、添加`@GlobalTransactional`注解。最后通过流程图详解一阶段提交与二阶段回滚/提交的内部机制。

### 经典金句/数据
> “Seata的做法是在Phase1就将本地事务提交，这样就可以省去Phase2持锁的时间，整体提高效率。”
> “每个RM使用DataSourceProxy连接数据库……在第一阶段将undo_log和业务数据放在一个本地事务提交。”
