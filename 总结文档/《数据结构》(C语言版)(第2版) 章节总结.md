# 《数据结构》(C语言版)(第2版) 章节总结

## 目录说明

总结依据该书目录与正文对应关系，按8章结构逐章整理。部分内容参考了严蔚敏经典教材《数据结构》(C语言版)及《数据结构与算法分析》的相关内容作为补充。

## 第1章：绪论

### 1. 核心论点

本章主要回答：数据结构是什么？为什么要学习数据结构？本章确立了“数据结构是相互之间存在一种或多种特定关系的数据元素的集合”这一定义，并指出**程序设计 = 数据结构 + 算法**这一核心公式。

### 2. 关键概念/事件

- **数据(Data)**：客观事物的符号表示，能输入计算机并被程序处理的符号总称。(p.5)
- **数据元素(Data Element)**：数据的基本单位，计算机程序中通常作为一个整体考虑和处理。(p.5)
- **数据结构(Data Structure)**：相互之间存在一种或多种特定关系的数据元素的集合。(p.6)
- **逻辑结构与物理结构**：逻辑结构指数据元素间的逻辑关系（集合、线性、树形、图形）；物理结构指数据在计算机中的存储形式（顺序存储、链式存储）。(p.7-9)
- **抽象数据类型(ADT)**：一个数学模型及定义在该模型上的一组操作，由数据对象、数据关系和基本操作三部分组成。(p.11-12)

### 3. 逻辑推演/叙事脉络

本章从计算机从数值计算向非数值计算发展的背景出发，通过图书馆书目检索、人机对弈、交通灯管理三个案例，引出数据结构的研究对象。随后，逐步定义数据、数据元素、数据对象等基本概念，明确数据结构的定义。接着区分逻辑结构与物理结构，介绍四种基本逻辑结构和两种存储结构。最后引入抽象数据类型的概念及其描述方法，为后续各章的数据结构定义奠定基础。

### 4. 经典金句/数据

> “程序设计 = 数据结构 + 算法” (p.5)

> “数据结构是一门研究非数值计算的程序设计问题中计算机的操作对象以及它们之间的关系和操作等的学科。” (p.3)

## 第2章：线性表

### 1. 核心论点

本章回答：如何表示和操作具有一对一关系的数据序列？核心论点是：线性表是n个数据元素的有限序列，可采用顺序存储（顺序表）或链式存储（链表）实现，两种结构在插入/删除和查找操作上各有优劣。

### 2. 关键概念/事件

- **线性表(List)**：零个或多个数据元素的有限序列，元素之间存在一对一的线性关系。(p.21)
- **顺序表(Sequential List)**：用一组地址连续的存储单元依次存储线性表的数据元素，可随机存取，但插入删除需移动大量元素。(p.25-27)
- **链表(Linked List)**：用一组任意的存储单元存储数据元素，通过指针链接，插入删除方便但不支持随机存取。(p.31-34)
- **单链表、循环链表、双向链表**：链表的三种基本形式，分别适用于不同场景。(p.40-42)
- **一元多项式的表示与相加**：线性表的典型应用案例，可用顺序表或链表存储稀疏多项式。(p.47-51)

### 3. 逻辑推演/叙事脉络

本章首先给出线性表的抽象数据类型定义。接着介绍顺序存储结构，分析其查找、插入、删除操作的时间复杂度（插入删除平均移动一半元素，O(n)）。然后引入链式存储结构，详细讲解单链表的查找、插入、删除、整表创建和删除操作，并讨论头指针与头结点的作用。随后扩展到循环链表和双向链表。最后通过一元多项式相加案例，展示线性表在实际问题中的应用，并对比顺序表与链表的性能差异。

### 4. 经典金句/数据

> “顺序存储结构的插入与删除操作，平均要移动表中一半元素。”(p.30)

> “链式存储结构不要求逻辑上相邻的元素在物理位置上也相邻，因此没有顺序存储结构所具有的弱点，但同时也失去了顺序表可随机存取的优点。”(p.39)

> 顺序表与链表的比较：顺序表适合频繁查找、很少插入删除的场景；链表适合频繁插入删除、长度变化大的场景。(p.70)

## 第3章：栈和队列

### 1. 核心论点

本章回答：如何实现后进先出(LIFO)和先进先出(FIFO)两种特殊线性结构？核心论点是：栈和队列是操作受限的线性表，栈在表尾（栈顶）插入删除，队列在一端（队尾）插入、另一端（队头）删除，分别适用于递归函数调用、表达式求值、排队模拟等场景。

### 2. 关键概念/事件

- **栈(Stack)**：限定仅在表尾进行插入或删除的线性表，后进先出(LIFO)。(p.56-57)
- **队列(Queue)**：只允许在一端插入、另一端删除的线性表，先进先出(FIFO)。(p.58-59)
- **递归与栈**：递归函数调用通过系统栈（递归工作栈）管理活动记录，每层递归产生一个工作记录压栈。(p.63-70)
- **循环队列**：解决顺序队列“假溢出”问题，通过模运算实现队头队尾循环。(p.72-74)
- **表达式求值（算符优先法）**：栈的经典应用，通过运算符栈和操作数栈实现中缀表达式求值。(p.80-82)

### 3. 逻辑推演/叙事脉络

本章从栈的定义和抽象数据类型开始，分别实现顺序栈和链栈的进栈、出栈操作。然后讨论递归的实现机制，分析递归工作栈的状态变化。接着介绍队列的定义，详细讲解循环队列（解决假溢出）和链队列的实现。最后通过四个案例（数制转换、括号匹配、表达式求值、舞伴问题）展示栈和队列的实际应用。

### 4. 经典金句/数据

> “栈的修改是按后进先出的原则进行的，因此栈又称为后进先出(LIFO)的线性表。” (p.56)

> “队列是一种先进先出(FIFO)的线性表。最早进入队列的元素最早离开。”(p.58)

> 循环队列队空条件：Q.front == Q.rear；队满条件：(Q.rear+1) % MAXQSIZE == Q.front。(p.73)

## 第4章：串、数组和广义表

### 1. 核心论点

本章回答：如何存储和操作字符串、多维数组及广义表？核心观点是：串是内容受限的线性表（元素为字符）；数组可视为线性表的推广；广义表则允许元素本身为子表，具有递归结构。KMP算法通过next数组避免了模式匹配中的回溯。

### 2. 关键概念/事件

- **串(String)**：由零个或多个字符组成的有限序列，空串与空格串的区别。(p.89-90)
- **模式匹配**：子串在主串中的定位操作，BF算法时间复杂度O(n×m)，KMP算法优化至O(n+m)。(p.94-100)
- **数组的顺序存储**：以行序为主序（C语言）或以列序为主序（FORTRAN），通过映像函数计算元素地址。(p.101-102)
- **稀疏矩阵的压缩存储**：三元组顺序表、行逻辑链接的顺序表、十字链表。(p.102-104)
- **广义表(Generalized List)**：元素可以是原子或子表的线性表，表头、表尾操作，递归性质。(p.104-107)

### 3. 逻辑推演/叙事脉络

本章先介绍串的定义、存储结构和基本操作，重点讲解BF模式匹配算法及其低效问题，引出KMP算法的改进思想，详细推导next数组和nextval数组的计算方法。然后转向多维数组，讨论顺序存储的地址计算和特殊矩阵（对称、三角、对角）的压缩存储。最后介绍广义表的递归定义、存储结构（头尾链表和扩展线性链表）及递归算法（求深度、复制、建立）。

### 4. 经典金句/数据

> “KMP算法的最大特点是指示主串的指针不需回溯，整个匹配过程中对主串仅需从头至尾扫描一遍。” (p.99)

> 串的模式匹配算法中，next函数的定义：
>
> - next[1] = 0
> - next[j] = Max{k | 1<k<j 且 't1...t(k-1)' = 't(j-k+1)...t(j-1)'}
> - 其他情况 next[j] = 1 (p.97)

## 第5章：树和二叉树

### 1. 核心论点

本章回答：如何表示和处理具有一对多层次关系的数据？核心论点是：二叉树是最常用的树形结构，具有递归性质；二叉查找树支持O(log n)平均时间的查找、插入和删除；哈夫曼树是最优二叉树，用于数据压缩编码。

### 2. 关键概念/事件

- **树(Tree)**：n个结点的有限集，有且仅有一个根结点，其余结点分为互不相交的子树。(p.113-114)
- **二叉树(Binary Tree)**：每个结点至多有两棵子树的树，左右子树有次序之分。(p.115)
- **二叉树的遍历**：先序、中序、后序、层序四种遍历策略，递归与非递归实现。(p.124-130)
- **二叉查找树(Binary Search Tree)**：左子树所有结点值小于根，右子树所有结点值大于根，支持动态查找。(p.73-79, 英文原版)
- **线索二叉树(Threaded Binary Tree)**：利用空指针域存储前驱和后继信息，便于遍历。(p.130-134)
- **哈夫曼树(Huffman Tree)**：带权路径长度最小的二叉树，用于哈夫曼编码实现数据压缩。(p.138-144)

### 3. 逻辑推演/叙事脉络

本章从树的定义和基本术语开始，介绍树的三种存储结构（双亲表示法、孩子表示法、孩子兄弟表示法）。然后重点讨论二叉树，包括性质、顺序和链式存储、四种遍历方式及推导遍历结果的方法。接着介绍线索二叉树的构造和遍历。之后通过孩子兄弟表示法实现树、森林与二叉树的转换。最后详细讲解哈夫曼树的构造算法和哈夫曼编码的生成，并给出案例分析。

### 4. 经典金句/数据

> “二叉树的深度为k时，至多有2^k - 1个结点。” (p.120)

> 二叉树性质3：对任何一棵二叉树T，如果其终端结点数为n0，度为2的结点数为n2，则n0 = n2 + 1。(p.120)

> 哈夫曼树构造：每次选取两个权值最小的树合并，重复直至只剩一棵树。(p.139)

## 第6章：图

### 1. 核心论点

本章回答：如何表示和处理具有多对多网状关系的数据？核心论点是：图由顶点和边（弧）组成，可采用邻接矩阵或邻接表存储；深度优先搜索(DFS)和广度优先搜索(BFS)是图的两种基本遍历方法；最小生成树、最短路径、拓扑排序和关键路径是图的经典应用算法。

### 2. 关键概念/事件

- **图的定义**：G=(V,E)，V是顶点集，E是边（弧）集。有向图、无向图、完全图、连通图、强连通图等术语。(p.151-153)
- **存储结构**：邻接矩阵（数组表示法）、邻接表、十字链表（有向图）、邻接多重表（无向图）。(p.155-162)
- **图的遍历**：深度优先搜索(DFS)和广度优先搜索(BFS)，时间复杂度O(n+e)（邻接表）或O(n²)（邻接矩阵）。(p.163-167)
- **最小生成树(Minimum Spanning Tree)**：Prim算法（加点法，O(n²)，适合稠密图）和Kruskal算法（加边法，O(e log e)，适合稀疏图）。(p.167-172)
- **最短路径**：Dijkstra算法（单源点，O(n²)）和Floyd算法（所有点对，O(n³)）。(p.172-177)
- **拓扑排序**：AOV网（顶点表示活动），检测有向无环图(DAG)，O(n+e)。(p.178-180)
- **关键路径**：AOE网（边表示活动），求工程最短完成时间，O(n+e)。(p.180-186)

### 3. 逻辑推演/叙事脉络

本章首先给出图的定义和基本术语（度、路径、连通分量等）。然后介绍四种存储结构，重点对比邻接矩阵和邻接表。接着讲解DFS和BFS两种遍历方法，并通过连通分量和生成树的例子说明遍历的应用。之后分节讨论图的应用：最小生成树（Prim和Kruskal算法）、最短路径（Dijkstra和Floyd算法）、拓扑排序（AOV网）、关键路径（AOE网）。每类算法都给出详细步骤和复杂度分析。

### 4. 经典金句/数据

> “具有n个顶点的连通图，其生成树有且仅有n-1条边。” (p.153)

> Dijkstra算法：按路径长度递增的次序产生最短路径。(p.173)

> 拓扑排序：在有向图中选一个无前驱的顶点输出，删除该顶点和以它为尾的弧，重复直至全部输出或不存在无前驱顶点。(p.179)

## 第7章：查找

### 1. 核心论点

本章回答：如何在海量数据中高效找到特定记录？核心论点是：查找算法可分为基于比较的查找（顺序、折半、树表）和散列查找（直接映射）。折半查找适用于有序顺序表（O(log n)）；二叉排序树支持动态插入删除（平均O(log n)）；散列表在理想情况下可实现O(1)的查找效率。

### 2. 关键概念/事件

- **平均查找长度(ASL)**：查找算法效率的度量标准，ASL = ΣPi·Ci。(p.194)
- **折半查找**：仅适用于有序顺序表，判定树深度为⌊log₂n⌋+1，ASL≈log₂(n+1)-1。(p.196-198)
- **二叉排序树(BST)**：左子树<根<右子树，中序遍历得有序序列。查找、插入、删除平均O(log n)。(p.200-206)
- **平衡二叉树(AVL树)**：左右子树高度差绝对值≤1，保证最坏情况O(log n)。四种旋转调整：LL、RR、LR、RL。(p.207-211)
- **B-树/B+树**：多路平衡查找树，适用于外存文件索引。m阶B-树每个结点有⌈m/2⌉~m棵子树。(p.212-221)
- **散列表(Hash Table)**：通过散列函数直接计算存储位置，处理冲突的方法有开放定址法（线性探测、平方探测、双散列）和链地址法。(p.221-230)

### 3. 逻辑推演/叙事脉络

本章先介绍查找的基本概念和ASL定义。然后依次讲解静态查找表的三种方法（顺序、折半、分块查找），重点分析折半查找的判定树和ASL。接着进入动态查找表，介绍二叉排序树的查找、插入、删除操作及其平均分析，引出平衡二叉树的调整方法。随后简要介绍B-树和B+树的外存索引原理。最后详细讲解散列表，包括散列函数构造方法、冲突处理策略及性能分析。

### 4. 经典金句/数据

> “折半查找在查找成功时进行比较的关键字个数最多不超过树的深度，即⌊log₂n⌋+1。” (p.198)

> 散列表的平均查找长度是装填因子α的函数，而不是记录个数n的函数。(p.228)

> B-树定义：一棵m阶B-树，除根外所有非终端结点至少有⌈m/2⌉棵子树。(p.212)

## 第8章：排序

### 1. 核心论点

本章回答：如何将一组无序数据按关键字有序排列？核心论点是：排序算法可按内部/外部、稳定/不稳定分类；简单排序（插入、冒泡、选择）时间复杂度O(n²)；高效排序（希尔、堆、归并、快速）时间复杂度O(n log n)；基数排序则通过分配收集实现线性时间排序。

### 2. 关键概念/事件

- **排序的稳定性**：关键字相等的记录在排序前后相对位置不变则算法稳定。(p.236)
- **插入排序**：直接插入O(n²)但正序时O(n)；希尔排序（缩小增量）突破O(n²)。(p.237-242)
- **交换排序**：冒泡排序（O(n²)）；快速排序（平均O(n log n)，最坏O(n²)）。(p.242-248)
- **选择排序**：简单选择排序（O(n²)）；堆排序（O(n log n)，不稳定）。(p.248-256)
- **归并排序**：2-路归并，时间O(n log n)，空间O(n)，稳定。(p.256-258)
- **基数排序(Radix Sort)**：多关键字排序，LSD法，时间O(d(n+rd))，稳定。(p.258-262)
- **外部排序**：多路归并、置换-选择排序、最佳归并树。(p.262-269)

### 3. 逻辑推演/叙事脉络

本章首先介绍排序的基本概念（稳定性、内部/外部）和待排序记录的存储方式。然后按类别逐一讲解各类排序算法：插入类（直接插入、希尔）、交换类（冒泡、快速）、选择类（简单选择、堆）、归并类（2-路归并）、分配类（基数排序）。每类算法从基本思想出发，给出实现代码、复杂度分析和稳定性判断。最后对各类排序算法进行综合比较，给出适用场景建议，并简要介绍外部排序的多路归并、置换-选择排序和最佳归并树。

### 4. 经典金句/数据

> “快速排序是平均情况下最快的内部排序方法。”(p.268)

## 第1章：理解 RuntimeClass 与使用多容器运行时
**来源文件：** 【理解 RuntimeClass 与使用多容器运行时】+贾之光+2020.4.6.pdf

### 核心论点
- **解决的问题**：随着 Kubernetes 支持多种容器运行时（如 runc, kata, gVisor），如何解决不同运行时混用、Pod 调度匹配以及资源开销统计的问题？
- **核心观点**：RuntimeClass 是 Kubernetes 中用于抽象和选择容器运行时的全局资源，通过 `Handler` 指定运行时，通过 `Scheduling` 实现节点亲和，通过 `Overhead` 精确统计资源开销，从而实现多运行时的精细化管理。

### 关键概念/事件
- **RuntimeClass**：Kubernetes v1.14 引入的全局域资源，用于表示一个容器运行时。它解耦了 Pod 定义与具体运行时实现。
- **Handler**：对应 CRI 配置中的容器运行时名称，由 Kubelet 调用对应的 handler 来处理 Pod。
- **Overhead**：Kubernetes v1.16 引入，用于统计 Pod 除容器本身外的额外资源开销（如 Kata 容器的 Guest Kernel 内存）。该值会参与调度、ResourceQuota 和驱逐判断。
- **Scheduling**：包含 `NodeSelector` 和 `Tolerations`，用于确保 Pod 被调度到支持特定 RuntimeClass 的节点上。注意：用户需手动为节点打上相应 Label。

### 逻辑推演/叙事脉络
本章首先回顾了 Kubernetes 容器运行时的演进历史，从唯一的 Docker 到支持 rkt，再到通过 CRI 支持 kata、gVisor 等，引出多运行时并存带来的管理难题（如何选择、如何调度、如何统计开销）。接着，详细介绍了 RuntimeClass 的资源定义结构（Handler, Overhead, Scheduling），解释了各字段的作用及相互关系。随后，通过一个具体的多运行时示例（runc 和 runv/kata），展示了从配置 containerd、创建 RuntimeClass 资源到部署 Pod 的完整流程。最后总结了 RuntimeClass 的核心价值及其在资源统计和调度中的注意事项。

### 经典金句/数据
> “RuntimeClass 是 Kubernetes 一种内置的全局域资源，主要用来解决多个容器运行时混用的问题。”

> “Pod Overhead 最终会永久注入到 Pod 内并且不可更改。即便是 RuntimeClass 被删除或更新也是如此。”

## 第2章：理解 CNI 和 CNI 插件
**来源文件：** 【理解 CNI 和 CNI 插件】+溪恒+2020.3.9.pdf

### 核心论点
- **解决的问题**：Kubernetes 如何实现 Pod 网络的联通？如何选择合适的网络插件？如何开发自定义网络插件？
- **核心观点**：CNI (Container Network Interface) 是 Kubernetes 网络的标准 API 接口，通过插件化机制实现网络配置。选择 CNI 插件需综合考虑环境限制、功能需求（如 NetworkPolicy）、性能需求（Overlay vs Underlay）等因素。

### 关键概念/事件
- **CNI (Container Network Interface)**：容器网络接口标准，Kubelet 通过调用符合 CNI 标准的插件二进制文件来配置 Pod 网络。
- **CNI 插件实现模式**：
    - **Overlay**：通过隧道（如 VXLAN, IPIP）打通网络，不依赖底层网络，适用于虚拟化环境，但性能有损耗。
    - **路由**：通过路由表打通，部分依赖底层网络，性能较好。
    - **Underlay**：直接利用底层网络能力（如 SR-IOV, BGP），强依赖底层，性能最好，适用于物理机或对性能要求极高的场景。
- **CNI 工作流程**：1. 配置 CNI 配置文件；2. 安装 CNI 二进制插件；3. Kubelet 监听 Pod 创建；4. 执行 CNI 插件配置网络（分配 IP、创建 veth pair、配置路由）。

### 逻辑推演/叙事脉络
本章首先介绍了 Kubernetes Pod 网络联通的基本原理（无 NAT 互通）及 Service 的工作原理。接着定义了 CNI 的概念及其在 K8s 中的使用流程（配置文件+二进制插件）。随后，重点讨论了如何选择适合的 CNI 插件，对比了 Overlay、路由、Underlay 三种模式的优缺点及适用场景（物理机、虚拟化、公有云、安全需求等）。之后，简要介绍了开发 CNI 插件的两个核心部分：给 Pod “插上网线”（配置网卡、IP、路由）和“连上网络”（Daemon 进程管理集群网络打通）。最后提出了课后思考与实践方向。

### 经典金句/数据
> “适合的才是最好的，从环境限制、功能需求、性能需求去考虑选择 CNI 插件。”

> “Overlay 性能相对较差，Underlay 模式和路由模式网络插件性能好。”

## 第3章：调度器的调度流程和算法介绍
**来源文件：** 【调度器的调度流程和算法介绍】+汪萌海（木苏）+2020.1.6.pdf

### 核心论点
- **解决的问题**：Kubernetes 调度器如何将 Pod 分配到合适的 Node？其内部架构、算法流程及扩展机制是怎样的？
- **核心观点**：Kubernetes 调度器通过 Filter（预选）和 Priority（优选）两阶段算法选择节点，并通过 Scheduler Framework 提供丰富的扩展点，允许用户自定义调度逻辑，以满足复杂的调度需求（如 GPU 调度、打散策略等）。

### 关键概念/事件
- **调度流程**：Queue -> PreFilter -> Filter (Predicates) -> PostFilter -> Score (Priorities) -> Reserve -> Permit -> PreBind -> Bind -> PostBind。
- **Predicates (预选)**：硬约束，如资源充足性、端口冲突、节点亲和/反亲和、卷约束等。不满足则直接剔除节点。
- **Priorities (优选)**：软约束，打分排序。包括资源水位（LeastRequested/MostRequested）、Pod 打散（EvenPodsSpread）、亲和性打分等。
- **Scheduler Extender**：早期的扩展机制，通过 HTTP 调用外部服务进行 Filter/Score/Bind，但存在性能瓶颈和单点限制。
- **Scheduler Framework**：新一代调度框架，提供多个扩展点（Plugin），支持同步/异步扩展，解决了 Extender 的性能和灵活性问题。

### 逻辑推演/叙事脉络
本章首先介绍了调度器的整体架构，包括队列管理、调度循环、缓存机制等。接着深入讲解了调度算法的两个核心阶段：Predicates（过滤不满足条件的节点）和 Priorities（对剩余节点打分排序），并详细列举了常见的 Predicate 和 Priority 策略（如资源水位计算、打散算法公式）。随后，介绍了如何配置调度器（配置文件、参数调整）。之后，对比了旧的 Scheduler Extender 机制和新的 Scheduler Framework，重点阐述了 Framework 的各个扩展点及其用途（如 Reserve 用于状态管理，Permit 用于 Gang Scheduling）。最后说明了如何编写和注册自定义 Plugin。

### 经典金句/数据
> “Predicates 解决‘能不能放’的问题，Priorities 解决‘放哪里更好’的问题。”

> “Scheduler Framework 通过扩展点用途和并发模型，实现了更灵活、高效的调度逻辑定制。”

## 第5章：可观测性：你的应用健康吗？
**来源文件：** 【可观测性：你的应用健康吗？】+刘中巍（莫源）+2019.11.13.pdf

### 核心论点
- **解决的问题**：应用迁移到 K8s 后，如何保障其健康稳定？如何快速诊断问题并进行远程调试？
- **核心观点**：通过 Liveness 和 Readiness 探针实现应用的健康检查与自愈/流量隔离；通过 `kubectl describe`、Events、Logs 三步法诊断问题；利用 `kubectl exec`、Port-Forward、Telepresence 等工具进行远程调试。

### 关键概念/事件
- **Liveness Probe (存活探针)**：判断容器是否存活。失败则重启容器。适用于死锁、无法恢复的错误场景。
- **Readiness Probe (就绪探针)**：判断容器是否准备好接收流量。失败则将 Pod 从 Service Endpoint 中移除。适用于启动慢、临时负载高场景。
- **探测方式**：httpGet, tcpSocket, exec。
- **问题诊断三步法**：1. `kubectl describe pod` 查看状态和事件；2. 查看 Events 获取详细信息；3. 查看 Pod 日志确定应用内部错误。
- **远程调试工具**：
    - `kubectl exec`：进入容器内部。
    - `kubectl port-forward`：将远程服务端口映射到本地。
    - `Telepresence`：将本地开发环境代理到集群中，或反之。

### 逻辑推演/叙事脉络
本章首先提出了应用上云后的健康保障需求。接着详细对比了 Liveness 和 Readiness 探针的定义、行为差异、适用场景及配置参数（initialDelaySeconds, periodSeconds 等），强调了合理配置阈值的重要性。随后，介绍了常见应用异常（Pending, Waiting, Crashing, Running 但不工作）的诊断思路，并总结出“描述-事件-日志”的三步排查法。最后，介绍了多种应用远程调试手段，包括进入容器、端口转发以及使用 Telepresence 进行更高级的双向代理调试。

## 第2章：Pod 与容器设计模式

### 核心论点
本章深入探讨“为什么我们需要 Pod”，指出 Pod 是 Kubernetes 中实现“容器设计模式”的核心机制。Pod 本质上是“进程组”，解决了单个容器无法有效管理多进程协作及资源共享的问题，是 Kubernetes 调度的原子单位。

### 关键概念/事件
- **Pod = 进程组**：类比 Linux 中的线程组，Pod 是一组紧密协作、共享资源的容器集合，是 K8s 的最小调度单位。
- **Infra Container (Pause 容器)**：每个 Pod 中都有一个特殊的 Pause 容器，负责持有 Network Namespace，使 Pod 内其他容器共享同一个 IP 和网络栈。
- **Sidecar 模式**：通过在 Pod 中定义专门容器来执行辅助工作（如日志收集、代理、监控），实现主业务与辅助功能的解耦。
- **Init Container**：在主容器启动前按顺序执行的初始化容器，用于准备环境或数据（如下载 WAR 包）。

### 逻辑推演/叙事脉络
作者首先通过类比 Linux 进程与线程的关系，引出 Pod 作为“进程组”的概念，解释了单容器模型在处理多进程应用时的局限性（如 PID 1 问题）。接着，详细阐述了 Pod 的实现机制，重点讲解了如何通过 Infra 容器共享网络命名空间，以及通过 Volume 共享存储。最后，详解了三种主要的容器设计模式：Init Container（初始化）、Sidecar（边车，用于日志、代理、适配器），强调了这些模式如何实现功能的解耦与重用。

## 第3章：Kubernetes 中的服务发现与负载均衡

### 核心论点
本章解决 Kubernetes 中 Pod IP 动态变化导致的服务访问难题，介绍了 Service 资源对象如何提供稳定的虚拟 IP 和负载均衡能力。核心观点是 Service 通过 Label Selector 关联后端 Pod，屏蔽了 Pod 的生命周期细节，实现了服务发现与内部/外部暴露。

### 关键概念/事件
- **Service**：Kubernetes 中的服务抽象，提供稳定的 ClusterIP、DNS 名称和负载均衡能力。
- **ClusterIP**：集群内部的虚拟 IP，通过 iptables/IPVS 规则将流量转发到后端 Pod。
- **Headless Service**：设置 `clusterIP: None`，不进行负载均衡，DNS 直接解析到后端 Pod 的 IP 列表，适用于状态应用或客户端自主选择场景。
- **服务暴露类型**：ClusterIP（仅集群内）、NodePort（节点端口映射）、LoadBalancer（云厂商负载均衡器）、ExternalName（外部服务别名）。

### 逻辑推演/叙事脉络
课程从需求来源入手，指出 Pod IP 易变且需要统一入口的问题。随后解读 Service 的用例，展示其 YAML 结构（Selector, Ports, Type）。接着通过操作演示，说明如何在集群内通过 DNS、环境变量或直接 IP 访问 Service。最后深入架构设计，讲解 Kube-Proxy 如何利用 iptables/IPVS 实现流量转发，以及 CoreDNS 如何实现服务名解析，并简要介绍了不同 Service 类型如何将服务暴露给外部网络。

## 第4章：etcd 性能优化实践

### 核心论点
本章聚焦于 Kubernetes 核心组件 etcd 的性能瓶颈与优化策略。作者指出 etcd 作为强一致性的 KV 存储，其性能受限于磁盘 IO、网络 RTT 及内部锁竞争，需从 Server 端（硬件、算法、配置）和 Client 端（使用习惯）两方面进行优化。

### 关键概念/事件
- **性能瓶颈点**：Raft 共识算法的网络 RTT、WAL 日志的磁盘 fsync 延迟、Boltdb 的索引锁竞争。
- **Server 端优化**：使用 SSD 硬盘、优化内存索引层锁、调整 Boltdb batch size、优化 Lease 回收算法、启用完全并发读。
- **Client 端最佳实践**：避免 Put 大 Value、避免频繁创建/删除 Key、复用 Lease、减少 Watch 的数量和范围。
- **Raft 与存储**：etcd 基于 Raft 算法保证一致性，数据持久化依赖 WAL（预写日志）和 Snapshot（快照）。

### 逻辑推演/叙事脉络
首先回顾 etcd 的基本架构（Raft、WAL、Boltdb）。接着分析影响 etcd 性能的关键因素，包括网络、磁盘 IO 和内部软件机制。随后分两部分展开优化实践：Server 端重点介绍硬件选型（SSD、专用网卡）和软件层面的改进（如 Segregated Hashmap、Lease 优化）；Client 端则列举了常见的错误用法（如大 Value、频繁变更 Node 状态）并给出建议。最后总结强调理解瓶颈和遵循最佳实践的重要性。

### 经典金句/数据
> “etcd 被设计为提供高可用、强一致的小型 KeyValue 数据存储服务。”

> “Put 时避免大 value，精简再精简！……避免创建频繁变化的 key/value……避免创建大量 lease，尽量选择复用”

## 第5章：GPU 管理和 Device Plugin 工作机制

### 核心论点
本章阐述 Kubernetes 如何通过 Device Plugin 机制管理 GPU 等异构资源。核心观点是 K8s 原生不支持具体硬件管理，而是通过扩展资源（Extended Resources）和设备插件框架，将设备发现、健康检查和分配逻辑外包给第三方插件，从而实现 GPU 的容器化调度。

### 关键概念/事件
- **Device Plugin**：K8s 的插件机制，允许第三方设备提供商以 gRPC 方式向 Kubelet 注册设备，上报资源数量并处理分配请求。
- **Extended Resources**：通过 Device Plugin 上报的非内置资源（如 `nvidia.com/gpu`），调度器可据此进行 Pod 调度。
- **GPU 容器化原理**：通过挂载 NVIDIA 驱动目录和设备文件（`/dev/nvidia*`）到容器中，解决 CUDA 版本依赖问题。
- **工作流程**：注册（Register）-> 监听（ListAndWatch）-> 分配（Allocate）-> 创建容器（CreateContainer）。

### 逻辑推演/叙事脉络
首先介绍管理 GPU 的需求（加速部署、提升利用率、资源独享）。接着讲解 GPU 容器化的基础，即如何在 Docker 中映射驱动和设备。然后深入 K8s 的 GPU 管理，介绍 Device Plugin 的工作机制：插件启动后向 Kubelet 注册，Kubelet 将资源信息同步给 API Server，调度器根据资源请求调度 Pod，最后 Kubelet 调用插件的 Allocate 接口获取设备路径并创建容器。最后指出了当前机制的缺陷（如调度精细度不足）及社区解决方案。

### 经典金句/数据
> “Device Plugin Framework：允许第三方设备提供商以插件外置的方式对设备的调度和全生命周期管理。”

> “如果 CUDA 版本不匹配，应用无法运行。通过容器镜像解决 CUDA 版本依赖的问题。”
